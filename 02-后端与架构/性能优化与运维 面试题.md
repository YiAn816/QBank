## 1. 不同型号设备的性能差异很大，端侧Agent怎么适配？

#性能优化 #系统设计 #端侧AI

### 知识点
- 分类：性能优化、系统设计、端侧AI
- 设备能力检测
- 动态模型选择
- 运行时决策

### 答案

我会在首次运行和关键状态变化时检测芯片能力、可用内存、系统版本、电量、温度和网络，再按能力档位选择模型大小、量化精度、上下文长度和并发数。低端或过热设备降级到规则、小模型或获准的云端能力，并保证核心功能仍可用。策略通过远程配置和灰度更新，但隐私数据是否上云必须单独授权；最后在真实机型矩阵上验证质量、P95 延迟、耗电和崩溃率。

### 解析

通过检测和动态决策实现多设备适配。

## 2. 常见大模型推理引擎有哪些？推理关注哪些指标？

#推理引擎 #性能优化

### 知识点
- 分类：推理引擎、性能优化
- 常见推理服务与引擎：vLLM、TensorRT-LLM、TGI、SGLang 等
- 推理指标：吞吐、首token延迟、总延迟、显存占用、并发能力、模型兼容性
- 不同业务对吞吐和延迟权重不同

### 答案

常见方案包括 vLLM、TensorRT-LLM、TGI 和 SGLang 等。选型时我会用目标模型和真实请求分布评估首 Token 延迟、逐 Token 延迟、端到端延迟、吞吐、显存占用、并发稳定性和兼容性。在线交互更看尾延迟，离线批处理更看吞吐；还要比较量化、并行、监控和运维成本，不能只看单一峰值。

### 解析

推理引擎和指标选择需根据实际业务需求权衡。

## 3. 大规模Agent系统的多线程和多进程资源调度怎么设计？

#系统设计 #并发编程 #性能优化

### 知识点
- 分类：系统设计、并发编程、性能优化
- 任务拆成可调度单元
- CPU密集型走进程池，IO密集型走异步或线程池
- 配合队列、优先级、流控、熔断和资源隔离

### 答案

我会先把检索、工具、推理和后处理拆成有资源画像的任务。I/O 密集调用优先异步化；Python 中不能释放 GIL 的 CPU 密集任务可放进程池或独立服务，能释放 GIL 的原生计算则按实测选择线程。调度层设置有界队列、优先级、公平配额、超时、取消和背压，并按租户与任务类型隔离资源。模型推理通常交给专用批处理服务，不能让业务线程直接争抢 GPU。

### 解析

IO密集和CPU密集分开处理，配合完善的调度机制。

## 4. 大量NPC同时在线如何控制推理成本

#系统设计 #性能优化

### 知识点
- 分类：系统设计、性能优化
- 轻量模型降级
- 交互范围判断
- 长期记忆加载时机
- 公共私有状态分离

### 答案

我会按玩家可见性、交互距离和剧情重要度分层。远端 NPC 用规则、状态机或低频批量更新；进入交互范围后再加载相关记忆并调用小模型，关键角色或复杂对话才升级强模型。公共世界事件生成一次摘要复用，私有状态按 NPC 隔离；相似请求可批处理和缓存。系统还要设置每帧、每区域和每玩家预算，超限时保证游戏主循环不被推理阻塞。

### 解析

通过距离判断降级模型和延迟加载记忆来控制推理成本。

## 5. 当Runbook与当前系统版本不匹配怎么办？

#运维 #自动化 #配置管理

### 知识点
- 分类：运维、自动化、配置管理
- Runbook绑定服务版本和验证时间
- 检查时过滤不适用文档
- 执行前再检查环境，不匹配就停止自动操作

### 答案

Runbook 应绑定服务、版本范围、环境、依赖前提、最近验证时间和负责人。Agent 检索时先过滤不适用版本，执行前再读取实际部署、配置和资源状态，逐条校验前置条件；任何关键条件不匹配，就降级为只读诊断并通知值班人员。修订后的 Runbook 要在预生产演练、人工审核并重新签名发布，不能由模型临时改写后直接执行。

### 解析

版本绑定加环境检查，版本不匹配时必须停止自动操作。

## 6. 端侧Agent的评测指标有什么特别？

#系统设计 #性能优化 #测试

### 知识点
- 分类：系统设计、性能优化、测试
- 多维度指标
- 资源消耗
- 稳定性评估

### 答案

端侧除任务质量，还要在真实设备矩阵上测首响应、P95/P99 延迟与抖动、内存峰值、耗电、温度、崩溃率和安装包体积，并覆盖弱网、断网、前后台切换和长时间运行。云端评测更关注集群吞吐、资源利用和服务成本；端侧还必须评估设备差异、隐私、离线能力和用户可感知的发热卡顿。

### 解析

端侧评测需涵盖性能和稳定性指标，纯质量评估不够全面。

## 7. 多个服务同时出问题，Agent怎么决定优先级？

#运维 #系统设计

### 知识点
- 分类：运维、系统设计
- 按业务影响排序
- 优先处理用户可见的核心链路
- 评估故障扩散风险，正在扩散的先处理
- 资源有限时集中力量恢复最关键服务

### 答案

我会按用户影响、数据安全、SLO 错误预算消耗速度、故障扩散趋势和恢复难度排序，而不是按告警数量。先处理会继续放大或影响核心交易的共同根因，同时保护仍健康的依赖；安全与数据损坏风险通常优先于局部性能下降。Agent 给出处置队列和依据，跨业务取舍由事故负责人确认，并随指标变化动态重排。

### 解析

强调资源分配策略，核心是按业务影响和扩散风险优先级处理。

## 8. 多个Agent同时处置关联故障，如何防止动作互相冲突？

#分布式 #系统设计 #运维

### 知识点
- 分类：分布式、系统设计、运维
- 所有变更先写入统一事故计划
- 执行器按资源锁和动作依赖串行提交冲突操作
- 冲突出现时统一重算计划版本

### 答案

所有 Agent 先把建议写入同一个版本化事故计划，只有中心执行器能修改生产。计划声明目标资源、前置条件、依赖、互斥组和预期后置条件；同一资源的冲突动作通过租约或 fencing token 串行化，提交时再做版本检查。执行后写回真实状态，计划过期或人工接管时立即取消后续动作，不能只靠 Agent 之间互发消息协调。

### 解析

统一计划编排加资源锁加串行执行加冲突重算，防止多Agent动作冲突。

## 9. 多模态Agent延迟怎么优化？

#系统设计 #AI/机器学习 #性能优化

### 知识点
- 分类：系统设计、AI/机器学习、性能优化
- 任务链路分级
- 预处理缓存
- 模型分级调用
- 轻量链路

### 答案

我会先分解链路，不是每次都调用最重模型。OCR、图像缩略特征和向量表示可在内容版本不变时预处理并缓存，在线按任务风险与难度路由模型；解码、OCR、安全检测和检索能并行的尽量并行。低风险内容先走轻量链路，置信度不足再升级。优化前先测各阶段 P95/P99，避免缓存过期结果或为了快跳过必要检查。

### 解析

通过预处理缓存和模型分级，降低不必要的计算开销。

## 10. 多租户环境下怎么做成本隔离？

#系统设计 #运维

### 知识点
- 分类：系统设计、运维
- 模型调用按租户计量
- 检索和工具配额按租户统计
- 单租户突发流量限流熔断

### 答案

我会把输入输出 Token、GPU 时间、检索、存储和工具费用都归集到租户与场景，设置预算、并发、速率和队列配额。调度采用公平队列或加权份额，单租户突发先排队、限流或路由到降级模型，不能挤占系统保底容量。大客户可使用预留资源或独立池，并提供用量告警和成本明细；限额策略也要防止大量小请求绕过。

### 解析

成本隔离需要从模型调用、资源使用等多个维度按租户独立计量，并对异常流量做限流熔断保护，防止单租户影响整体服务。

## 11. 多Agent的可观测性怎么做？

#系统设计 #架构 #运维

### 知识点
- 分类：系统设计、架构、运维
- 每个Agent有traceID
- 记录输入输出工具调用和耗时
- 主链路能看到DAG
- 失败能定位规划错工具错还是合并错

### 答案

一次任务使用统一 Trace ID，每个 Agent、模型和工具调用建立独立 Span，记录角色、版本、状态、耗时、重试和脱敏后的输入输出摘要。界面能还原计划、执行、合并和验收的 DAG，并通过责任 Agent 与证据 ID 定位错误。线上指标按角色和组合统计成功率、尾延迟、冲突、循环、人工介入和链路长度，避免整体成功率掩盖某个 Agent 空转。

### 解析

通过traceID和DAG可视化实现全链路可观测性，快速定位问题环节。

## 12. 高并发Agent系统里怎么优化召回和生成延迟？

#系统设计 #性能优化 #Agent系统

### 知识点
- 分类：系统设计、性能优化、Agent系统
- 召回阶段：缓存、并行检索、语义分片、粗排加精排
- 生成阶段：流式输出、KV Cache、批处理、超时降级
- 监控P95延迟，区分模型延迟、检索延迟、工具调用延迟

### 答案

我会先把排队、查询理解、各路召回、重排、模型 Prefill 和 Decode 分别打点，看 P50/P95/P99。检索侧可并行独立召回、优化分片和索引、缓存带版本的安全结果，并用较大候选集加有限重排；生成侧裁剪上下文、复用前缀或 KV Cache、连续批处理和流式返回。每段都有超时预算、取消和降级，优化时同时看任务质量，不能用减少证据换取表面低延迟。

### 解析

分阶段优化，全链路监控是落地关键。

#运维

- 分类：运维
- 确认告警真实性
- 评估影响范围
- 关联服务、变更和指标

### 解析

避免误操作和资源浪费，优先获取诊断信息。

## 14. 告警平台自身故障时，运维Agent如何降级？

#运维 #高可用 #监控

### 知识点
- 分类：运维、高可用、监控
- 保留独立的指标与日志读取通道
- 无法确认状态时只提供诊断建议
- 所有写操作冻结并通知值班人员

### 答案

告警平台不能是唯一观察通道，我会保留独立的指标、日志、健康探针和云资源状态入口，并监控监控系统自身。主要信号不可用时，Agent 明确标记证据不完整，停止依赖这些信号的自动写操作，只提供有限诊断与安全降级建议，同时通知值班人员。恢复后对缺失窗口做数据补录和事故复盘，避免把“没有告警”误判成“系统健康”。

### 解析

独立通道保证只读能力，无法确认时降级为诊断模式，写操作冻结防止误操作。

### 解析

可观测性支撑问题排查和链路追溯。

## 16. 工具返回结果太大怎么办

#系统设计 #性能优化

### 知识点
- 分类：系统设计、性能优化
- 工具先分层过滤摘要
- 返回关键字段和引用ID
- 大文件长列表外部存储
- 避免上下文被撑爆

### 答案

工具接口应支持分页、字段选择、过滤和聚合，优先返回当前决策需要的结构化字段。大文件和长列表放外部存储，结果返回稳定引用 ID、总量、截断标识和生成时间；Agent 可按需继续查询。摘要必须可回链原始结果，高风险决策不能只相信有损摘要。还要限制单次大小、处理慢客户端，并防止工具内容中的间接 Prompt Injection。

### 解析

模型上下文窗口有限，工具返回必须精简，只提供必要信息。

## 17. 路线工具返回慢怎么优化？

#性能优化 #系统设计

### 知识点
- 分类：性能优化、系统设计
- 缓存策略
- 常用地点缓存
- 路线摘要缓存
- 实时路况限查
- 超时降级处理

### 答案

我会先分解地理编码、路线计算、实时路况和下游排队，确认慢点。静态地点和不含实时状态的路线骨架可按版本缓存，实时路况使用短 TTL 或事件更新，并对同类请求合并；多个候选可并行但限制扇出。设置端到端超时预算和熔断，超时时返回带时间戳的非实时方案或请用户稍候，不能把过期路况伪装成实时结果。

### 解析

通过缓存减少实时查询，超时场景要给用户确定性反馈。

## 18. 你怎么做工作流观测才能快速定位问题

#系统设计 #运维 #Java

### 知识点
- 分类：系统设计、运维、Java
- 打通instance_id、node_id、request_id
- 关注成功率、平均时长、卡住时长、重试率、补偿率
- 日志支持按实例完整回放

### 答案

每个工作流实例有稳定 `instance_id`，节点执行有 `node_id` 和 attempt，外部调用关联 Trace 与幂等键。状态转换以事件方式持久化，记录开始、等待、成功、失败、重试、补偿和人工介入。指标看吞吐、成功率、各节点 P95/P99、排队与卡住时长、重试和补偿率；界面能按实例回放当时的工作流、模型、Prompt 和工具版本，快速定位静默挂起。

### 解析

很多线上事故不是报错而是流程静默挂起，需要全链路追踪能力。

## 19. 排障上下文怎么组织？

#运维 #系统设计

### 知识点
- 分类：运维、系统设计
- 按服务、时间窗口、错误类型聚合
- 保留监控指标趋势和异常点
- 日志抽样去重保留代表性错误
- 拼成事件序列形成可推理事故现场

### 答案

不能把所有日志塞给模型。我会按服务、时间窗、错误类型、Trace 和版本聚合，保留指标趋势、异常点、错误分布和少量代表样本，再把发布、配置和依赖变化拼成时间线。原始数据放在可按引用 ID 回查的存储中，模型针对当前假设逐步取证。摘要过程要保留采样规则和缺失信息，避免去重后掩盖低频但严重的错误。

### 解析

上下文组织决定Agent推理质量，需要结构化聚合而非堆砌原始日志。

## 20. 如果错误记忆被多个Agent使用导致订单推荐错了怎么处理

#AI #系统设计 #运维

### 知识点
- 分类：AI、系统设计、运维
- 记忆下线并清缓存
- 引用链路找出受影响任务

## 33. 为什么需要PD分离？业界方案通常如何实现？

- 分类：性能优化、推理引擎
- PD分离：Prefill和Decode阶段拆分优化
- Prefill更吃算力和带宽
- Decode更关注持续生成和缓存管理
- 分离后可独立扩缩容，提高资源利用率
- 常见方案：分层、调度和KVCache管理

### 解析

PD分离通过拆分不同特性的阶段实现资源优化配置。

## 54. KVCache是什么？为什么能提升推理速度？

#深度学习 #LLM #性能优化

### 知识点
- 分类：深度学习、LLM、性能优化
- 缓存历史Token的Key和Value矩阵
- 生成下一个Token时避免重复计算上下文
- 优化自回归推理延迟，但增加显存占用
- 长上下文需考虑淘汰和压缩策略

### 答案

KV Cache 保存 Transformer 各层历史 Token 的注意力 Key 和 Value。自回归生成下一个 Token 时，只需计算新 Token 的表示，并与缓存的历史 K/V 做注意力，避免每一步重新对整个前缀做前向计算，因此显著降低解码开销。代价是缓存随层数、序列长度、并发和 K/V 头数增长，占用大量显存；工程上会用分页管理、量化、前缀复用、淘汰或卸载来权衡吞吐与延迟。

### 解析

理解缓存机制的核心原理及其对推理性能的影响。
