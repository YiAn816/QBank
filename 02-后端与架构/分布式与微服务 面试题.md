## 1. 第三方 MCP 工具如何实现租户隔离？

#MCP #多租户 #安全

### 知识点
- 短期凭证与最小 Scope
- 进程、文件和网络隔离
- 返回结果标记来源并禁止跨任务复用

### 答案

每次调用都使用绑定租户、用户、工具和有效期的短期凭证，MCP Server 运行在受限进程或沙箱中，只允许访问授权文件、网络和密钥。消费者还要重新校验资源归属，不能只相信模型传来的租户 ID。

工具结果带租户、任务和数据范围元数据，缓存与日志沿用相同边界，默认禁止跨任务和跨租户复用。

### 解析

短期凭证只解决授权时效，完整隔离还需要执行环境、数据、缓存和审计全链路配合。

## 2. 调用超时且下游可能已经成功时，怎么避免重复提交？

#幂等 #故障恢复

### 知识点
- 超时不等于失败
- 只读有限重试，写操作使用稳定幂等键
- 状态查询和结果复用

### 答案

先区分只读和有副作用调用。只读操作可以退避后有限重试；写操作必须在第一次调用前生成稳定幂等键，并让下游原子记录执行状态和结果。

超时后优先按幂等键查询状态，同一个键重试时返回原结果；状态未知且下游不支持幂等时暂停并进入对账或人工处理，不能生成新请求重复提交。

### 解析

分布式超时产生的是“不确定结果”。只有端到端幂等和状态查询才能安全恢复。

## 3. 端云协同时怎么保证状态一致性？

#端云协同 #数据一致性

### 知识点
- 稳定对象 ID、版本和操作日志
- 离线写入与冲突检测
- 业务化合并而非简单最后写入获胜

### 答案

端和云围绕同一个对象 ID、版本向量或递增版本维护状态，端侧离线操作记录为可重放事件，联网后把事件上传并与云端版本比较。没有冲突就增量合并，有冲突则按字段和业务语义处理。

删除、支付等高风险动作不能只按时间戳覆盖；需要删除标记、条件写入或人工确认。同步过程还要幂等，并保留冲突和合并记录。

### 解析

设备时间并不绝对可信，“后写覆盖前写”会丢操作。答案应说明版本、离线事件和业务冲突策略。

## 4. 多个 Agent 的结论冲突怎么办？

#多Agent #冲突处理

### 知识点
- 比较证据、来源、版本和权限
- 业务规则由确定性系统裁决
- 无法判断时请求人工确认

### 答案

我不会简单投票，而会让每个结论携带证据、来源、时间、版本和适用范围。汇总器先验证证据，再按权威性和新鲜度合并；工具实测结果通常高于无依据推断。

涉及权限、金额等业务规则时交给确定性规则裁决，证据仍冲突则保留分歧并请求用户或人工确认，不能让另一个模型凭感觉仲裁。

### 解析

冲突处理的对象是证据和规则，而不是 Agent 数量或语言说服力。

## 5. 多个 Agent 抢同一个任务怎么办？

#任务调度 #并发控制

### 知识点
- 原子领取和租约
- 心跳、超时回收和幂等
- 防止锁过期后的双执行

### 答案

任务领取使用队列原子消费、条件更新或带期限的租约，成功领取后记录 Worker、版本和过期时间。执行者定期续约，崩溃后由调度器回收任务。

租约过期可能出现两个执行者并存，所以最终写操作仍要幂等或带 fencing token，拒绝旧持有者提交结果。

### 解析

分布式锁不能单独保证业务只执行一次，租约、隔离令牌和最终写入幂等需要配合。

## 6. 多租户 Agent 平台需要隔离哪些资源？

#多租户 #资源隔离

### 知识点
- 身份、数据、模型、工具和执行环境
- 缓存、日志、队列和向量索引
- 配额、成本和故障域

### 答案

至少隔离身份和凭证、业务数据、记忆与向量索引、缓存和日志、消息队列、工具权限、执行沙箱，以及模型调用和成本配额。共享组件的每次请求都要携带可信租户上下文并重新授权。

还要做资源和故障隔离，避免一个租户耗尽线程、GPU 或下游配额。隔离不仅是防止看到别人的数据，也包括防止互相拖垮。

### 解析

租户边界贯穿同步、异步和观测链路，任何漏传上下文的后台任务都可能成为突破口。

## 7. 多 Agent 的分工怎么设计才不乱？

#多Agent #架构设计

### 知识点
- 按责任和权限边界划分
- 输入输出 Schema 与验收标准
- 避免重复决策和职责重叠

### 答案

我会按责任和权限划分，而不是为了多 Agent 硬拆角色。规划者输出任务与验收标准，检索者只提供带来源的证据，执行者只做授权动作，评审者依据标准判断结果。

每个角色有明确输入输出 Schema、工具范围和失败处理，编排器负责依赖与状态。两个 Agent 如果长期处理同一输入并做同一决策，就应合并。

### 解析

分工的价值是降低耦合和权限范围；角色名称很多并不等于架构合理。

## 8. 多 Agent 的共享状态和上下文怎么管理？

#多Agent #状态管理

### 知识点
- 权威任务存储和版本化更新
- 公共结构化状态与私有上下文分离
- 最小必要共享和冲突检测

### 答案

共享状态放在权威任务存储中，记录目标、子任务、证据引用、工具结果和版本；更新采用 CAS、事务或事件日志，避免并发覆盖。每个 Agent 只获取完成任务需要的视图，私有草稿不直接广播。

跨 Agent 传递结构化消息并带来源和版本，冲突时重新读取、合并或人工确认。模型上下文只是状态视图，不能成为唯一事实来源。

### 解析

该题同时考察一致性和最小暴露。全量共享聊天记录既浪费 Token，也会扩散错误和敏感信息。

## 9. 多 Agent 协作时任务分配怎么设计？

#多Agent #任务调度

### 知识点
- 任务 DAG、依赖和验收标准
- 能力、权限、成本与负载匹配
- 动态重分配和失败降级

### 答案

规划层把目标拆成带输入、输出、依赖、权限和验收标准的任务 DAG，再根据 Agent 能力、工具权限、成本和当前负载分配。可并行节点并行，存在数据依赖的节点保持顺序。

计划和分配结果持久化；Agent 超时或失败时依据任务重要性重试、换执行者、降级或转人工，不能靠 Agent 自由协商形成隐式流程。

### 解析

规划 Agent 只是实现选择，关键是任务契约、调度策略和可恢复状态。

## 10. 工具调用怎么做监控？

#可观测性 #工具调用

### 知识点
- 成功、错误、超时、重试和尾延迟
- 选择、参数、无效调用和副作用指标
- 按工具、版本、租户和任务切片

### 答案

基础指标包括调用量、成功率、错误码、P95/P99 延迟、超时和重试；Agent 侧还要看工具选择准确率、参数校验失败、无效调用、重复写入和越权拦截。

指标按工具版本、租户和任务类型切片，并用 Trace 关联模型决策与下游结果。异常样本进入评测集，但日志要脱敏并控制访问。

### 解析

只看接口成功率无法判断 Agent 是否选错工具或虽然调用成功却完成了错误动作。

## 11. 工具返回结果太大，如何避免撑爆上下文？

#上下文工程 #工具调用

### 知识点
- 服务端过滤、分页和字段投影
- 大对象外置并返回引用
- 按需读取与摘要可追溯

### 答案

优先让工具支持查询过滤、分页和字段投影，只返回当前步骤需要的数据。大结果写入对象存储或结果表，模型只得到 Schema、摘要、统计和受权限保护的引用。

后续按需读取片段，并保留原始结果版本和来源。摘要不能替代权威数据，高风险决策要回到原始字段复核。

### 解析

核心是减少进入模型的数据，而不是把大结果完整返回后再截断。

## 12. 工具链问题如何端到端排查？

#可观测性 #故障排查

### 知识点
- Trace ID 和父子调用关系
- 模型、Prompt、Schema 与工具版本
- 参数摘要、状态变化和结果

### 答案

为一次任务生成 Trace ID，每次模型和工具调用建立 Span，记录 Prompt、模型、Schema、工具版本、参数摘要、授权决策、重试、延迟和结果状态，并关联父子关系。

排查时寻找第一个偏离预期的节点，而不是只看最终错误。敏感参数脱敏或用引用代替，但要保留足够字段做关联和回放。

### 解析

日志多不等于可观测，版本、因果关系和状态变化才是端到端定位的关键。

## 13. 工具或 MCP Schema 变更怎么兼容？

#API设计 #MCP

### 知识点
- 版本化与向后兼容
- 新增可选字段，破坏性变更使用新版本
- 双版本窗口和契约测试

### 答案

工具注册中心维护不可变 Schema 版本，新增字段尽量可选并提供默认语义；删除、改名或类型变化属于破坏性变更，应发布新版本并保留迁移窗口。

网关根据明确版本校验或做可审计转换，线上记录实际版本。Prompt、客户端和评测集同步更新，通过契约测试和灰度确认后再下线旧版。

### 解析

网关转换不能掩盖语义变化。向后兼容、版本选择和弃用流程需要同时设计。

## 14. 多个 NPC 对同一世界事件记忆不同，怎么保持剧情一致？

#事件溯源 #状态管理

### 知识点
- 权威世界事件流
- 公共事实与角色视角分离
- 版本重建和有意的不完整认知

### 答案

公共世界事实由权威事件流维护，每个事件有 ID、版本和时间；NPC 记忆是基于其可见范围生成的角色视图，只能表达知道什么和如何理解，不能反向改写公共事实。

状态冲突时从权威事件重建视图。角色不知道或记错可以是剧情设计，但必须明确是角色认知，而不是系统数据不一致。

### 解析

一致性不要求所有 NPC 知道相同内容，而是公共事实唯一、角色视图可解释且可重建。

## 15. 推荐场景为什么可能使用多 Agent，而不是单 Agent？

#多Agent #推荐系统

### 知识点
- 意图、召回、排序、解释和安全边界不同
- 并行与专业化收益
- 先证明复杂度值得

### 答案

当意图理解、内容检索、安全审核和解释生成使用不同数据、工具或权限，并且部分任务可以并行时，多 Agent 能缩小每个角色的上下文和权限，也便于独立评测。

但召回和排序这类稳定算法服务不必强行包装成 Agent。只有专业化、隔离或并行收益超过额外延迟、成本和排错复杂度时才值得采用。

### 解析

题目不应预设多 Agent 一定更好。关键是说明使用条件和替代方案。

## 16. 端侧离线删除后，云端旧状态又把内容恢复了，怎么修？

#端云协同 #删除语义

### 知识点
- 删除作为带版本的事件或墓碑
- 同步时检测版本和冲突
- 墓碑保留与垃圾回收

### 答案

删除不能表现为“本地记录消失”，而要生成带对象 ID、版本和时间的删除事件或 tombstone。同步时云端看到墓碑后阻止旧版本复活，并把删除传播到其他设备。

墓碑在所有副本确认前不能过早清理；并发编辑与删除按业务规则合并，高风险删除还要支持审计和恢复期。

### 解析

事件溯源是一种方案，真正关键是让删除成为可同步、可比较版本的显式状态。

## 17. 支付前校验通过，但执行时库存变了怎么办？

#并发控制 #库存系统

### 知识点
- 校验与执行之间存在竞态
- 预占、条件更新或事务
- 失败后释放和补偿

### 答案

不能依赖支付前的一次读取。下单时由库存服务使用预占、带版本条件更新或数据库原子扣减，只有库存条件仍满足才进入后续支付；冲突则返回明确结果并重新选择。

如果支付与库存跨系统，要设计超时释放、支付失败补偿和对账，避免扣了库存没支付或支付成功没订单。

### 解析

“再读一次库存”仍有检查后变化的窗口，最终保障必须是原子条件写入或预占协议。

## 18. 如何测试一次改动没有破坏租户边界？

#多租户 #安全测试

### 知识点
- 相同资源 ID 的跨租户负向样本
- API、缓存、异步、搜索和日志全链覆盖
- 并发、权限变化与回归阻断

### 答案

创建多个租户并故意使用相同资源 ID、相似内容和不同权限，验证合法访问成功、跨租户访问始终失败。测试覆盖 API、缓存、消息队列、对象存储、向量检索、批处理和后台补偿。

再加入并发、权限撤销、缓存命中和故障重试场景。任何跨租户命中都作为发布阻断项，并检查审计是否能准确定位。

### 解析

只测正常路径不够，租户漏洞经常出现在缓存和异步恢复等旁路。

## 19. 如何用 AI 工具生成前后端代码？

#AI编程 #软件工程

### 知识点
- 明确技术栈、契约和验收标准
- 小步生成与人工审查
- 测试、安全和依赖治理

### 答案

先提供技术栈、目录约束、接口契约、数据模型、错误语义和验收标准，再按模块小步生成。前端明确状态、交互和边界态，后端明确鉴权、校验、事务、日志和测试。

每批变更通过 Diff 审核、自动测试、静态分析和依赖安全检查，再集成到主分支。AI 生成的是候选实现，责任仍由开发流程承担。

### 解析

核心不是提示词写得长，而是给出可验证契约，并把生成纳入正常工程质量体系。

## 20. MCP 和 Function Calling 有什么区别？系统如何支持 MCP？

#MCP #FunctionCalling

### 知识点
- Function Calling 描述模型如何提出结构化调用
- MCP 规范客户端与 Server 的能力交互
- 连接、权限、生命周期和审计

### 答案

Function Calling 主要解决模型用结构化参数表达“想调用哪个函数”；MCP 则规范客户端与 Server 之间如何发现和使用工具、资源等能力。两者可以配合：模型产生调用意图，MCP 客户端负责连接具体 Server。

后端需要管理 Server 来源与版本、连接生命周期、工具 Schema、权限、超时、日志和返回内容隔离，不能把协议支持等同于安全信任。

### 解析

二者不完全处于同一层级。实际能力会随实现和版本演进，回答应抓住模型接口与外部协议的边界。

## 21. 三步调用中第二步成功但回包丢失，如何恢复？

#工作流 #幂等

### 知识点
- 每步状态、业务主键和幂等键持久化
- 恢复时查询而非盲目重做
- 从确认成功的下一步继续

### 答案

工作流在调用第二步前持久化执行意图和幂等键，下游以该键原子执行并保存结果。恢复时先查询第二步状态；确认成功就补记结果并从第三步继续，明确失败才用同一键重试。

如果状态长期未知，则进入对账或补偿，不能凭工作流本地没有回包就认定下游未执行。

### 解析

这是典型的分布式不确定结果，关键是下游幂等、状态查询和持久工作流。

## 22. 什么时候不适合用多 Agent？

#多Agent #架构选型

### 知识点
- 简单、线性和低风险任务
- 子任务强依赖、难以验证
- 额外成本大于收益

### 答案

目标明确、步骤固定、链路短的任务通常用单 Agent 加工具就够了。子任务频繁互相等待、共享大量上下文或无法独立验收时，多 Agent 只会增加同步、延迟和错误入口。

我会先用最简单架构跑通并测量瓶颈，只有单体上下文、权限隔离或并行能力成为明确问题时再拆分。

### 解析

多 Agent 是复杂度投资，不是系统高级程度的标志。

## 23. 什么时候多 Agent 才有价值？

#多Agent #架构选型

### 知识点
- 子任务可独立验收或并行
- 工具、知识或权限边界明显
- 专业化收益超过编排成本

### 答案

当任务能拆成边界清晰、可独立验证的子问题，或者不同子任务需要明显不同的工具、知识与权限时，多 Agent 才有价值。可并行研究、代码安全与性能分审等场景还能缩短总耗时。

上线前要用质量、延迟、成本和故障率与单 Agent 基线比较，不能只展示角色数量。

### 解析

价值来自专业化、隔离和并行，而不是让多个模型重复讨论同一个问题。

## 24. 实时语音 Agent 的链路怎么拆？

#语音技术 #流式处理

### 知识点
- VAD/回声消除、ASR、编排、LLM、TTS 和播放
- 阶段重叠与取消传播
- 会话状态机和分段延迟

### 答案

链路通常包括 VAD 与回声消除、流式 ASR、对话和工具编排、LLM、流式 TTS 与播放控制。ASR 稳定片段可提前触发理解，LLM 产生首批内容后开始合成，各阶段流水并行。

统一状态机传播打断与取消信号，防止旧转写继续驱动工具。监控端点检测、首转写、首 Token、首音频和端到端任务成功率。

### 解析

难点不是列组件，而是流式重叠、打断、状态一致性和延迟归因。

## 25. 为什么工作流要设计补偿动作？

#分布式事务 #Saga

### 知识点
- 跨系统操作可能部分成功
- 补偿不一定等于精确回滚
- 幂等、顺序和人工兜底

### 答案

跨多个外部系统的流程很难使用单个数据库事务，失败时可能已经创建订单、冻结额度或发送消息。补偿动作把这些已提交副作用恢复到业务可接受状态，例如取消订单或释放预占。

补偿本身要幂等、可重试并按依赖逆序执行；有些动作无法真正撤销，只能追加更正或人工处理。

### 解析

补偿是业务语义上的恢复，不保证回到物理上的原始状态。

## 26. 下单类工具为什么要做幂等？

#幂等 #订单系统

### 知识点
- 模型、网络和队列都可能重复
- 稳定业务幂等键
- 权威存储唯一约束

### 答案

模型可能重复规划，网络超时会重试，消息队列也可能重复投递，因此一次用户意图可能到达订单服务多次。所有重试使用同一个业务幂等键，服务端通过幂等记录或唯一约束只创建一次订单，并返回相同结果。

前端防抖和分布式锁只能减少重复，不能替代订单系统的最终幂等保障。

### 解析

Request ID 必须在同一业务意图的重试中保持稳定，否则无法去重。

## 27. 向量库如何避免跨租户召回？

#向量数据库 #多租户

### 知识点
- 独立索引或强制分区
- 写入和查询都绑定租户与 ACL
- 结果二次授权和负向测试

### 答案

高隔离或高合规租户使用独立实例或索引；共享索引时使用不可由调用方覆盖的租户分区，并让每个向量继承文档 ACL。检索服务根据可信身份自动追加过滤，不能让模型生成租户条件。

返回前再做资源级授权，缓存 Key 也包含同一安全范围，并用相同资源 ID 的跨租户样本持续测试。

### 解析

结果后置过滤只能作为补充，未授权向量不应进入 Rerank 或模型上下文。

## 28. 协作流程中某个 Agent 超时怎么处理？

#多Agent #超时治理

### 知识点
- 节点级 Deadline 和取消
- 关键与可选输出分级
- 重试、替代、降级或人工处理

### 答案

每个节点继承任务总 Deadline，并设置自己的超时和取消令牌。可选输出超时后可标记缺失继续；关键输出则根据错误类型有限重试、切换替代能力、降级或转人工。

超时后还要确认旧 Agent 和工具是否真正停止，避免迟到结果覆盖新结果；所有结果带任务版本，编排器只接收当前版本。

### 解析

超时处理不仅是跳过或等待，还涉及取消传播、迟到结果和整体时间预算。

## 29. 一个工具持续失败，如何避免拖累所有任务？

#熔断 #故障隔离

### 知识点
- 超时、舱壁和按错误类型熔断
- 备选工具或降级
- 半开探测和逐步恢复

### 答案

先用短超时和独立资源池隔离工具，避免连接和线程被耗尽；再按工具、租户和错误类型统计失败，达到阈值后熔断，快速失败或切换安全的备选方案。

恢复时用少量半开探测验证，再逐步放量。业务错误不能被当成基础设施故障无限重试。

### 解析

熔断负责停止失败扩散，舱壁负责限制资源影响，两者职责不同。

## 30. 异步任务脱离原请求后，怎么保证租户上下文不丢失也不被滥用？

#异步任务 #多租户 #安全

### 知识点
- 可信租户、主体和任务上下文
- 消费侧重新认证授权
- 子任务权限只能缩小

### 答案

消息携带受保护的租户、主体、任务 ID 和授权 Scope，消费者验证签名或从可信存储重新加载身份，并根据当前权限再次授权。缺失或冲突时拒绝执行。

派生子任务只能继承或缩小 Scope，不能自行扩大。重试、死信和补偿保留同一上下文，日志、缓存和工具也沿用租户边界。

### 解析

权限快照有助于追溯，但权限可能已经撤销，因此消费时仍需结合当前授权状态。

## 31. 用户打断时工具调用已经提交，如何保证业务状态一致？

#取消语义 #状态一致性

### 知识点
- 停止未提交动作
- 已提交动作查询状态而非假设取消
- 补偿或用户确认后处理新意图

### 答案

打断事件先取消尚未提交的生成和工具计划；已经发给下游的写调用不能假设被撤销，要按任务 ID 和幂等键查询最终状态。若已成功，根据业务决定保留、补偿或请求用户确认；若未知，先对账。

新意图如果依赖旧动作结果，必须等待状态明确，避免旧任务和新任务并发修改同一资源。

### 解析

取消模型输出、取消网络请求和撤销业务副作用是三件不同的事。

## 32. 用户打断语音 Agent 时，系统怎么处理？

#语音交互 #状态机

### 知识点
- 停止 TTS 和生成
- 判断纠正、补充或切换话题
- 传播取消并保护业务状态

### 答案

检测到用户说话后快速停止 TTS 播放，并取消仍可取消的生成。保存已播内容和当前任务状态，再判断新输入是纠正、补充还是切换任务，分别更新计划。

后台工具不能无条件沿旧意图继续；未提交动作取消，已提交动作按上一题的状态查询与补偿流程处理。

### 解析

打断不仅是音频体验问题，还涉及会话状态和真实工具副作用。

## 33. 怎么控制多 Agent 的成本和延迟？

#多Agent #成本治理

### 知识点
- 单 Agent 基线和按需拆分
- 并行、模型路由和上下文预算
- 最大轮次、工具次数和 Deadline

### 答案

先建立单 Agent 基线，只在明确瓶颈节点引入多 Agent。可独立任务并行，强依赖任务不要硬拆；简单子任务路由到小模型，并复用经过权限隔离的确定性结果。

为每次任务设置 Token、费用、轮次、工具调用、并发和总 Deadline，达到预算后降级或请求用户决策。监控边际质量收益，长期没有收益的角色应删除。

### 解析

成本控制不只是限制 Token，还包括并发、外部工具、尾延迟和编排开销。

## 34. 长流程任务怎么保存状态并从中断恢复？

#工作流 #故障恢复

### 知识点
- 节点输入、输出、版本和状态持久化
- 检查点和依赖失效
- 副作用节点幂等与对账

### 答案

每个节点开始前记录执行意图，完成后持久化输入版本、输出引用、状态和幂等键。恢复时从最近有效检查点开始，复用依赖未变化的结果，只重跑失败或受影响节点。

对于外部写操作，恢复前先查询实际状态；模型上下文和内存不能作为唯一进度记录。状态迁移还要版本化，支持工作流升级。

### 解析

“从最后成功节点继续”只是表面，关键是确认检查点仍有效以及副作用是否已经发生。

## 35. Agent 如何执行工具调用？

#Agent #工具调用

### 知识点
- 注册工具 Schema 和权限范围
- 模型产生候选调用
- 后端校验、执行和回填

### 答案

系统向模型提供当前任务允许使用的工具 Schema 和描述，模型根据意图生成候选工具与参数。后端随后做类型、权限、资源、风险、幂等和业务状态校验，必要时请求确认，校验通过才执行。

结果以带来源和状态的结构化消息回填，模型决定继续调用还是回答。循环必须有次数、时间和成本上限，并记录完整 Trace。

### 解析

模型只提出调用意图，不能直接拥有执行权限；安全边界位于工具网关和业务服务。

## 36. 微服务拆分应遵循什么原则？

#微服务 #架构设计

### 知识点
- 业务能力和数据所有权
- 高内聚、低耦合与独立演进
- 避免分布式单体

### 答案

我会围绕业务能力和数据所有权拆分，让一个服务对一组高内聚规则和数据负责，并能独立开发、部署和扩缩容。服务边界优先参考领域边界，而不是按数据库表或技术层机械拆分。

拆分后要检查跨服务调用和事务是否过多；如果大部分请求都同步穿过多个服务、发布必须一起进行，就可能形成分布式单体，应该重新合并边界。

### 解析

考点是服务边界和数据所有权。微服务的收益必须覆盖网络调用、数据一致性、部署和运维复杂度，否则模块化单体可能更合适。
