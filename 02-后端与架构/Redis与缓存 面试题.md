## 1. 布隆过滤器适合什么场景？

#Redis #数据结构

### 知识点
- 位数组和多个哈希函数
- 可能误判存在，不会误判不存在
- 不适合精确判断和普通删除

### 答案

布隆过滤器是一种空间效率很高的概率数据结构。查询结果为“不存在”时可以确定不存在；结果为“可能存在”时仍需查询真实存储，因为存在假阳性。

它适合缓存穿透防护、大规模去重预判等场景，不适合要求百分之百准确的判断。标准布隆过滤器也不支持安全删除；需要删除时可考虑计数布隆过滤器，但会增加空间和复杂度。

### 解析

面试重点是明确假阳性和假阴性的方向，并讲清它只能做前置过滤。

## 2. 工作流某个步骤失败时，如何局部重试而不重跑全流程？

#工作流 #故障恢复

### 知识点
- 节点状态和输出持久化
- 幂等、检查点和依赖版本
- 副作用节点单独处理

### 答案

我会把工作流建模为有状态 DAG，每个节点完成后持久化输入版本、输出、状态和幂等键。节点失败时从最近的有效检查点恢复，复用未变化的上游结果，只重跑失败节点及受它影响的下游节点。

Redis 可以做高性能状态或缓存，但关键状态需要可靠持久化。重试前还要确认外部写操作是否已经成功，避免把“调用超时”误当成“没有执行”。

### 解析

局部重试依赖可恢复状态、幂等和依赖失效判断，不是简单缓存每个节点输出。

## 3. 电商大促期间，如何降低 AI 导购的响应延迟？

#高并发 #性能优化

### 知识点
- 容量规划、限流与排队
- 缓存、并行和流式输出
- 降级和真实业务数据校验

### 答案

先按峰值做容量规划和压测，入口按租户或用户限流，并用队列保护推理服务。常见问题和公共商品知识可以使用经过版本与权限隔离的缓存；库存、价格和优惠必须实时查询权威服务。

链路上并行执行互不依赖的检索，使用模型批处理和流式输出降低首响。过载时切小模型、缩短上下文或返回结构化推荐，不能为了速度复用过期库存和价格。

### 解析

流式输出只改善感知延迟，缓存也不是万能方案。回答应同时覆盖吞吐、尾延迟、数据新鲜度和降级。

## 4. 调度 Agent 应该怎么评估？

#调度系统 #评测

### 知识点
- 调度正确率和端到端成功率
- 排队、执行和恢复延迟
- 公平性、资源利用与人工接管

### 答案

我会分三层评估：决策层看任务拆分、优先级和资源选择是否正确；执行层看成功率、重试、取消和异常恢复；系统层看排队时间、端到端延迟、资源利用率、公平性和成本。

还要按任务类型、优先级和故障场景切片，统计人工接管率与错误动作率。只看普通任务完成率会掩盖拥塞和恢复问题。

### 解析

调度器既要正确，也要高效、公平和可恢复，不能只用一个成功率指标概括。

## 5. 多租户共用 Agent 服务时，缓存怎么设计才不会串租户？

#缓存 #多租户 #安全

### 知识点
- Key 包含租户、身份范围、权限和数据版本
- 公共与私有缓存物理或逻辑分离
- 回填与读取二次校验归属
- 权限变化主动失效

### 答案

先明确缓存内容的安全作用域。私有缓存 Key 至少包含租户、用户或角色范围、场景、权限版本、数据版本和模型版本；只有能证明完全公开的内容才能跨租户共享，公共和私有缓存最好分桶或分实例。

统一缓存 SDK 生成 Key，并在回填、批量读取和反序列化后再次校验对象归属。权限或数据变化时主动失效，敏感缓存使用更短 TTL。TTL 只能缩短暴露时间，不能替代隔离。

### 解析

缓存隔离不是加一个 Tenant 前缀就结束，还要覆盖身份范围、版本、批量接口、回填和失效机制。

## 6. 分布式令牌桶限流怎么实现？

#Redis #限流

### 知识点
- 令牌数和最后补充时间
- Lua 脚本原子计算与扣减
- 时钟、过期和热点 Key

### 答案

可以在 Redis 保存当前令牌数和上次补充时间。每次请求由 Lua 脚本根据经过时间补充令牌、判断是否足够并原子扣减，同时限制桶容量，避免并发下超发。

实现时统一使用服务端时间或受控时钟，设置 Key 生命周期，并关注单个热点 Key 的吞吐。令牌桶允许一定突发；漏桶更强调平滑输出，滑动窗口则更直观地限制时间段请求数。

### 解析

核心是补充和扣减的原子性，以及算法在突发、公平和精度上的取舍。

## 7. 高并发会话下，如何保证 Agent 记忆读写性能和一致性？

#记忆系统 #缓存 #并发

### 知识点
- 权威存储与缓存职责分离
- 版本、幂等和异步写入
- Read-your-writes 与失效策略

### 答案

我会明确一个权威记忆存储，Redis 只承担会话态和热点缓存。写入先生成版本和幂等 ID；需要用户立即看到的新记忆，先更新会话状态或采用写穿策略，再异步完成向量化和长期索引。

读取时合并尚未归档的会话记忆和长期检索结果，并按 ID、版本去重。异步链路要有重试、死信、对账和延迟监控，不能宣称异步写入天然保证一致性。

### 解析

性能与一致性要先定义语义，例如是否要求 read-your-writes。Redis 加向量库不自动等于读写分离或一致。

## 8. 记忆召回怎么设计？

#记忆系统 #信息检索

### 知识点
- 权限、任务、时间和置信度过滤
- 混合召回与 Rerank
- 预算和冲突处理

### 答案

记忆召回不能只按向量相似度。我会先按用户权限、任务类型、适用范围和有效期过滤，再结合语义相似、关键词和时间衰减召回，最后 Rerank 并控制进入上下文的预算。

返回结果带来源、时间和置信度；互相冲突的记忆不直接合并成事实，而是按权威性排序或向用户确认。

### 解析

相似不等于适用。记忆系统尤其要避免无关旧信息和跨用户数据污染当前任务。

## 9. 什么信息应该写入长期记忆？

#记忆系统 #隐私

### 知识点
- 稳定、确认且跨会话有价值
- 临时信息保留在会话状态
- 来源、有效期和删除机制

### 答案

适合写入的是用户明确同意保存、相对稳定且以后仍有价值的信息，例如长期偏好和反复确认的工作习惯。寒暄、一次性任务、临时情绪和模型猜测只保留在当前会话。

每条长期记忆记录来源、时间、适用范围和有效期，并允许查看、更正和删除。敏感信息遵循数据最小化，不能默认长期保存。

### 解析

写入标准不应依赖某个游戏或角色场景，关键是稳定性、价值、授权和可治理性。

## 10. 企业知识库权限怎么与 RAG 检索结合？

#RAG #权限控制

### 知识点
- 文档和 Chunk 继承 ACL
- 检索前或检索中强制过滤
- 权限变化同步索引和缓存

### 答案

每个文档和 Chunk 都要带租户、资源归属和可验证的 ACL。查询时根据当前身份在检索阶段强制过滤，不能先把全量敏感内容送进 Rerank 或模型后再过滤。

权限变更后要同步索引、缓存和会话可见状态；高基数 ACL 可用分区索引、过滤检索或权限服务结合设计，但最终授权仍以权威系统为准。

### 解析

角色只是权限的一部分，还要考虑资源级授权。任何未授权内容都不应进入模型上下文。

## 11. 权限变更后，老会话怎么办？

#权限控制 #缓存

### 知识点
- 每次敏感访问重新授权
- 权限版本和缓存失效
- 清理会话中的敏感派生内容

### 答案

老会话不能永久沿用创建时的权限。每次检索和工具调用都依据当前身份重新校验，并用权限版本让旧缓存失效。

已经进入上下文的敏感摘要无法靠后端鉴权自动消失，因此权限收缩时要重建或终止相关会话，清理服务端缓存和派生状态；高风险场景要求用户重新认证。

### 解析

权限校验是持续过程。既要阻止新的访问，也要处理已缓存、已摘要的数据。

## 12. 权限策略升级后，如何验证历史缓存没有泄漏？

#缓存 #安全测试

### 知识点
- 策略版本与反向索引
- 主动失效和扫描
- 旧身份回放与负向测试

### 答案

缓存项记录策略版本、资源和主体范围，并维护可按资源或租户失效的索引。升级时主动删除不再满足策略的条目，而不是只等 TTL。

随后用旧 Token、降权账号和跨租户样本回放所有读取入口，检查缓存、批量接口和下游 CDN；监控旧版本命中并设置告警。

### 解析

验证不能只看删除任务是否成功，要从攻击者视角证明旧权限无法再命中数据。

## 13. 记忆写入队列阻塞时，如何避免对话读不到最新记忆？

#记忆系统 #消息队列

### 知识点
- 会话态作为 read-your-writes 缓冲
- 与长期结果合并去重
- 队列积压监控和降级

### 答案

写入长期存储前，先把新记忆以带版本的会话事件保存在可靠短期存储。读取时同时查询未归档事件和长期记忆，按记忆 ID 与版本合并，确保当前会话能读到自己的最新写入。

队列阻塞要告警、限流和重试，超过阈值时暂停非关键记忆写入或提示记忆暂未持久化。恢复后通过幂等消费和对账完成归档。

### 解析

双通道的重点不是“内存兜底”，而是明确 read-your-writes、可靠暂存和最终对账。

## 14. 推荐系统接口从 50 毫秒升到 2 秒，Agent 如何降级？

#降级 #推荐系统

### 知识点
- 超时、熔断和隔离
- 合规的缓存或静态候选
- 标记新鲜度并恢复探测

### 答案

先设置短超时和熔断，避免慢请求拖住 Agent 线程池；降级到最近且仍在有效期内的热门列表、规则候选或明确的无个性化结果。价格、库存等强时效数据仍需权威校验。

向用户说明当前推荐可能较通用，而不是用对话掩盖故障。后台通过半开探测逐步恢复，并记录降级率、任务成功率和数据新鲜度。

### 解析

缓存降级必须有适用范围和有效期。用户体验的关键是快速、诚实且不返回错误业务事实。

## 15. 新记忆和旧记忆冲突时怎么处理？

#记忆系统 #数据一致性

### 知识点
- 不直接覆盖
- 来源、时间、置信度和适用范围
- 权威规则或用户确认

### 答案

我不会直接用新内容覆盖旧内容，而是分别保存来源、时间、置信度和适用范围。系统先判断是否只是场景不同；确实冲突时按用户明确确认、权威来源和新鲜度决定，无法判断则向用户澄清。

更新采用版本化或事件记录，保留历史便于审计。权限、安全等关键事实不能仅按“最新一条”自动覆盖。

### 解析

记忆冲突是事实治理问题，不是简单的最后写入获胜。

## 16. Agent 根据过期位置做了错误调度并通知用户，怎么补救？

#实时系统 #事件响应

### 知识点
- 冻结错误调度并查询当前状态
- 重新规划和通知
- 新鲜度校验前置

### 答案

先停止该调度的后续动作，确认订单、司机和资源当前状态，再使用实时位置重新规划。若用户已经收到错误通知，要主动更正并说明变化；已经产生外部成本时按业务补偿。

修复上给位置快照加入采集时间和最大允许年龄，决策前强制校验，提交前再次确认关键资源没有变化。

### 解析

实时决策要处理状态在“读取—计算—执行”之间变化的问题，不能只在入口查一次位置。

## 17. 推荐 Agent 频繁读取历史行为，如何降低高并发延迟？

#推荐系统 #缓存 #FeatureStore

### 知识点
- 在线与离线特征分层
- 批量读取、缓存和预计算
- 新鲜度与回源保护

### 答案

把长期稳定特征离线聚合到 Feature Store，近期行为在流式链路更新，热点特征使用 Redis 等在线存储；推理时按用户批量读取一份特征快照，避免反复扫描原始日志。

缓存项带版本和新鲜度，设置回源限流与降级。还要监控特征缺失率和线上线下一致性，不能只追求读取速度。

### 解析

核心是特征预计算和冷热分层。原始行为日志不应成为在线推理的直接查询接口。

## 18. 什么是缓存穿透？如何处理？

#缓存 #Redis

### 知识点
- 不存在的数据反复绕过缓存
- 参数校验、空值缓存和布隆过滤器
- 限流与数据库保护

### 答案

缓存穿透是大量请求查询不存在的数据，缓存始终未命中，压力直接落到数据库。处理时先做参数和权限校验，再根据场景使用短期空值缓存或布隆过滤器，并配合限流和异常检测。

空值 TTL 不宜过长，避免真实数据创建后仍返回不存在；布隆过滤器也要处理初始化和更新一致性。

### 解析

穿透的对象是“不存在的数据”。它与热点 Key 失效造成的击穿、批量过期造成的雪崩不同。

## 19. 实时调度最怕什么？

#实时系统 #数据一致性

### 知识点
- 状态过期和并发变化
- 快照时间、版本和提交前复核
- 幂等与补偿

### 答案

最怕基于过期或彼此不一致的状态做不可逆决策。司机位置、订单和容量不断变化，因此每个数据都要带版本与时间，决策使用一致快照，并在执行前重新校验关键条件。

同时通过幂等、预占、条件更新和补偿处理并发冲突，而不是声称拿到了“绝对最新”的数据。

### 解析

实时系统无法保证所有数据永远最新，关键是定义新鲜度、检测冲突并安全处理状态变化。

## 20. 推荐商品生成后价格发生变化，怎么避免不一致？

#推荐系统 #数据一致性

### 知识点
- 模型只引用商品 ID 和价格快照
- 渲染与下单读取权威价格
- 展示时间和变更提示

### 答案

模型输出商品 ID 和推荐理由，价格由前端或服务端从权威价格中心读取，并带币种、地区和更新时间。若回答需要提到价格，也要标明快照时间，并在点击或下单时重新校验。

排查时关联生成时的商品快照、价格服务响应和用户点击时间，判断是缓存过期还是正常调价，不能让模型硬编码价格。

### 解析

价格属于高频变化的业务事实，应由权威系统负责，模型生成只承担表达。

## 21. 如何避免即时反馈导致推荐列表频繁震荡？

#推荐系统 #缓存

### 知识点
- 区分强否定和弱反馈
- 平滑更新、时间衰减和冷却
- 会话约束与长期画像分离

### 答案

先区分明确否定、跳过和短暂停留等反馈强度。明确的会话约束可以立即过滤，弱反馈则通过阻尼、时间衰减和最小更新间隔平滑影响排序，避免一次行为把长期权重清零。

临时黑名单可设置 TTL，但期限应由业务验证而非固定半小时。还要保留一定探索，防止列表过早收敛。

### 解析

稳定不等于忽略用户反馈，关键是作用域、反馈强度和更新速度。

## 22. 知识库文档更新怎么做增量索引？

#RAG #索引

### 知识点
- 变更事件、版本和幂等
- 新旧索引原子切换
- 删除同步、对账和回归

### 答案

文档新增、修改和删除都生成带文档 ID 与版本的事件，解析、切片、向量化和索引写入保持幂等。新版本全部写入并校验后再切换可见版本，避免查询到半更新状态。

删除要同步关键词索引、向量、缓存和派生摘要。失败通过重试和对账修复，发布后用检索回归验证相关问题。

### 解析

软删除可以支持回滚，但不是唯一方案；核心是版本化、原子发布和全链删除同步。

## 23. Agent 的长期记忆和短期上下文怎么分层？

#记忆系统 #上下文工程

### 知识点
- 会话态、用户记忆和任务结果
- 结构化状态与原始事件
- 授权、版本、有效期和删除

### 答案

短期上下文保存当前目标、约束、未完成事项和最近对话，可放在会话状态或 Redis；长期记忆保存经过确认且跨会话有价值的信息；任务产物则按业务对象进入权威存储，不要全部混成向量记忆。

原始事件、摘要和结构化状态分开管理。长期记忆带来源、版本、权限和有效期，并允许用户更正和删除。

### 解析

“Redis 短期、向量库长期”只是存储实现，不是完整的记忆分层设计。

## 24. Agent 多轮状态应该放在哪里？

#状态管理 #Agent

### 知识点
- 权威任务状态持久化
- 上下文仅携带必要视图
- 事件、摘要和工具结果分层

### 答案

真正决定任务进度的状态应放在可持久化、可并发控制的状态存储中，包括任务 ID、阶段、工具结果和待确认事项；模型上下文只携带当前调用需要的状态视图。

近期对话可以放会话缓存，长期事件进入数据库或对象存储，再按需摘要和检索。不能把上下文窗口当成唯一状态库。

### 解析

模型上下文会被截断且难以事务更新，业务状态和提示上下文必须分开。

## 25. 如何防止网络抖动导致重复下单？

#幂等 #订单系统

### 知识点
- 稳定幂等键
- 服务端原子去重和唯一约束
- 状态查询与结果复用

### 答案

用户确认下单时生成稳定幂等键，所有网络重试复用同一个键。订单服务在事务中以该键做唯一约束或幂等记录，第一次成功后保存订单结果，重复请求直接返回同一订单。

Redis 可以做快速防重，但最终保障应在权威订单存储中，避免 Redis 故障或过期导致重复。超时后先查询状态，不能换新键再次提交。

### 解析

核心是服务端端到端幂等。前端防抖和 Redis 锁都不能替代订单唯一约束。

## 26. ASR 中间结果不断变化，如何避免重复调用模型？

#语音技术 #缓存

### 知识点
- 稳定片段和端点检测
- 版本号、取消和去抖
- 预推理结果谨慎复用

### 答案

只对达到稳定阈值的 ASR 片段或检测到语义端点后触发正式推理；需要降低延迟时可以预推理，但每次请求绑定转写版本和取消令牌，新版本到来就废弃旧结果。

对相同稳定前缀做去抖和缓存，同时限制并发预请求。最终文本与预推理输入差异较大时必须重新生成，不能直接拼接旧答案。

### 解析

目标是在延迟和浪费之间取舍。缓存不能解决语义变化，版本和取消机制更关键。

## 27. 缓存穿透、击穿和雪崩分别是什么？

#缓存 #Redis

### 知识点
- 穿透：查询不存在数据
- 击穿：热点 Key 失效
- 雪崩：大量 Key 同时失效或缓存整体故障

### 答案

穿透是查询不存在的数据，常用参数校验、空值缓存和布隆过滤器；击穿是热点 Key 失效后大量请求同时回源，常用互斥重建、逻辑过期、请求合并和限流；雪崩是大量 Key 集中过期或缓存集群故障，需打散 TTL、多级缓存、容量隔离和降级。

热点永不过期并非通用答案，还要解决更新和数据陈旧问题。三类方案都应结合数据库保护和恢复流程。

### 解析

题目应称“缓存三大问题”，不是“RAG 三件套”；正确术语是缓存雪崩，不是“血崩”。

## 28. Redis 如何实现滑动窗口限流？

#Redis #限流

### 知识点
- Sorted Set 保存请求时间
- 清理、计数和写入原子化
- 唯一成员、过期和热点问题

### 答案

常见做法是用 Sorted Set，以请求时间为 score、唯一请求 ID 为 member。Lua 脚本原子完成删除窗口外记录、统计数量、判断限额并写入当前请求，同时给 Key 设置过期时间。

高流量下每个请求保存一条记录会消耗较多内存和 CPU，可按时间桶近似计数，或使用专门限流服务。还要明确边界时间和失败时放行还是拒绝。

### 解析

仅使用时间戳作 member 可能在同一毫秒覆盖请求，因此需要唯一 ID，并关注算法成本。

## 29. SSE 连接中断后，流式输出怎么恢复？

#SSE #流式处理

### 知识点
- 事件 ID 和持久化事件流
- Last-Event-ID 断点续传
- 任务状态、保留窗口和幂等

### 答案

不要把连接本身当成任务状态。每个生成任务有 task ID，每个 SSE 事件有递增 event ID，并把事件写入 Redis Stream 或消息表。客户端重连时携带 `Last-Event-ID`，服务端先补发缺失事件，再继续实时推送。

还要定义断线后模型任务是否继续、事件保留多久和多客户端如何消费。如果服务端已经取消生成，只能从检查点重新发起，不能承诺逐 Token 无缝续写。

### 解析

SSE 原生支持事件 ID 语义，但可靠恢复仍依赖服务端持久化、任务状态和明确的保留策略。
