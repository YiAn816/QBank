## 1. 调度Agent要维护哪些状态？

#消息队列 #分布式系统

### 知识点
- 分类：消息队列、分布式系统
- 任务队列维护
- 资源占用记录
- 优先级管理
- 执行结果追踪
- 唯一任务ID
- 任务状态持久化

### 答案

我会把状态分成四类。第一是任务状态，包括任务 ID、依赖关系、优先级、截止时间和当前阶段；第二是执行状态，包括负责的 Worker 或 Agent、租约、心跳和重试次数；第三是资源状态，比如并发额度、模型和工具占用；第四是结果与审计，包括输入版本、执行结果、错误原因和人工审批记录。

这些状态要持久化，并通过明确的状态机更新，不能只从对话文本里推断。还要处理超时、重复消息和执行方失联，确保任务能够恢复、取消和幂等重试。

### 解析

面试官关注的是调度系统能否在并发和故障下恢复。答案应覆盖任务、执行者、资源、结果和审计状态，并说明唯一 ID、状态机、租约和幂等机制。

## 2. 故障处理中模型服务不可用，运维Agent怎样降级？

#系统设计 #消息队列

### 知识点
- 分类：系统设计、消息队列
- 保留规则引擎和固定Runbook执行通道
- 高风险动作停止，只提供只读操作
- 从持久化检查点继续分析

### 答案

我会按能力和风险分级降级。模型不可用时，先停止依赖模型判断的高风险写操作，只保留监控查询、告警聚合以及经过审核的固定 Runbook；能够由规则引擎确定的低风险动作，可以在权限和参数校验后继续执行。

所有待处理任务、工具结果和审批状态都写入持久化检查点，并进入有上限的重试或延迟队列，避免故障期间形成重试风暴。模型恢复后从检查点继续，但执行前要重新校验告警是否仍有效，不能盲目补跑过期操作。

### 解析

考点是安全降级而非简单切换备用模型。完整回答应包括能力分级、只读或固定 Runbook、持久化状态、退避重试、恢复前重验和人工接管。

## 3. 会议 Agent 同时收到生成会议纪要和待办跟踪请求时，如何进行限流与队列管理？

#系统设计 #消息队列

### 知识点
- 分类：系统设计、消息队列
- 分布式任务队列
- 重度推理任务拆分多个Jobs
- Redis租户和会议室级并发限制
- WebSocket同步排队状态

### 答案

我会先按任务类型拆分队列：转写、纪要生成和待办提取可以形成有依赖关系的任务 DAG，避免重复处理同一份音频。入口按用户或租户做速率限制，执行端再按模型、GPU 和租户配额控制并发，并为交互型任务和后台长任务设置不同优先级。

每个任务都带幂等键、会议 ID 和版本号，消费者使用租约和可见性超时防止任务丢失。队列积压时可以降级模型或延后低优先级任务，前端通过 WebSocket 或轮询展示排队、进度和失败原因。Redis 可以实现部分限流能力，但持久任务状态不能只依赖临时计数器。

### 解析

这道题考察入口限流、资源并发、任务依赖、优先级、幂等和进度反馈的组合设计。回答不能只罗列 Redis、队列和 WebSocket，还要说明各组件分别解决什么问题。

## 4. 协调器主要做什么？

#系统设计 #消息队列

### 知识点
- 分类：系统设计、消息队列
- 负责路由分发
- 状态汇总
- 冲突裁决

### 答案

协调器负责把用户目标转成可调度的任务，选择合适的 Agent，管理依赖关系和共享状态，并在结果冲突、超时或失败时决定重试、降级还是转人工。它还应统一处理预算、权限、取消信号和执行轨迹。

协调器不应该承载所有业务逻辑，否则会变成难以扩展的“大 Agent”。业务能力仍由专业 Agent 或工具负责，协调器重点保证流程有序、状态一致和结果可追踪。

### 解析

考点是区分编排职责与业务职责。较完整的回答要覆盖路由、依赖、状态、异常、权限和预算，同时避免把协调器设计成新的单点瓶颈。

## 5. 异步任务、重试和死信队列中，如何保证租户隔离？

#消息队列 #系统设计

### 知识点
- 分类：消息队列、系统设计
- 显式传递可信的租户标识和身份信息
- 消费侧重新认证授权，不依赖线程变量
- 重试、补偿和死信回放保留租户上下文
- 缓存、存储、批处理和审计全链路隔离

### 答案

任务消息必须显式携带可信的租户标识、主体身份和任务 ID，并由生产端签名或通过受控消息系统传递；不能依赖线程变量，也不能只相信业务载荷里可被伪造的 Tenant ID。消费者恢复上下文后，要重新执行授权和资源归属校验，缺少或冲突时直接拒绝处理。

重试、补偿和死信回放必须保留同样的上下文，存储查询、缓存键、对象路径和工具调用也都要强制带租户边界。批处理可以为效率混合读取，但写入和事务边界必须保证不会串租户。最后通过跨租户负向测试和审计告警验证整个后台链路。

### 解析

核心不是简单地在消息头和消息体“双写”，而是建立可信身份、消费侧重新授权和全链路资源隔离。重复字段只能帮助发现不一致，不能替代身份验证。

## 6. 用户说“我的订单怎么变成两笔了”，排查方向是什么？

#系统设计 #消息队列

### 知识点
- 分类：系统设计、消息队列
- 查主Agent任务拆分日志看是否重复派发
- 查子Agent重试机制和幂等键
- 检查消息队列是否有重复投递
- 检查子Agent接收端幂等去重
- 问题可能在拆分任务层、投递层、执行层任意一处

### 答案

我会沿着同一个业务幂等键还原完整调用链。先确认客户端是否重复提交，再看主 Agent 是否重复拆分或派发任务；接着检查消息队列的至少一次投递、消费者超时重试和死信回放；最后确认订单服务是否在写入前做了幂等校验和唯一约束。

排查时重点关联任务 ID、消息 ID、调用 ID 和订单号，判断是“同一请求执行两次”还是“业务上确实创建了两个请求”。先停止继续重试并评估是否需要取消重复订单，修复后在最终写入层增加权威幂等保障，不能只依赖上游去重。

### 解析

这道题考察端到端幂等和可观测性。消息队列通常只能提供至少一次投递语义，真正防止重复订单的最后防线应在订单服务，包括幂等记录、唯一约束或状态机。

## 7. 怎么监控调度 Agent？

#系统设计 #消息队列

### 知识点
- 分类：系统设计、消息队列
- 队列长度监控
- 任务延迟监控
- 失败率监控
- 重试次数监控
- 优先级分布监控
- 降级策略

### 答案

我会从四层监控。入口层看请求量、限流和拒绝率；队列层看积压长度、最老消息年龄、各优先级等待时间和死信量；执行层看任务成功率、重试、超时、租约失效和资源利用率；业务层看端到端完成率、SLA 和错误动作比例。

所有指标都要按租户、任务类型、模型或工具版本切片，并用任务 ID 串起 Trace。告警应配套自动降级，例如暂停低优先级任务、限制重试、切换规则调度或转人工，而不是只做仪表盘。

### 解析

回答应体现技术指标与业务指标结合，以及从队列积压定位到具体任务的追踪能力。只看平均延迟容易掩盖尾延迟和个别租户饥饿问题。

## 8. Agent 之间传消息为什么不能只传自然语言？

#系统设计 #消息队列

### 知识点
- 分类：系统设计、消息队列
- 自然语言容易产生歧义
- 任务状态需要结构化
- 置信度和证据要明确

### 答案

自然语言适合表达开放内容，但不适合单独承担协议。Agent 之间的任务 ID、消息类型、状态、参数、证据引用、错误码、版本和截止时间都应该使用带 Schema 的结构化消息，下游才能稳定校验、重试和演进。

需要传递解释或用户原话时，可以把自然语言放在结构化字段中。这样既保留表达能力，又避免下游靠猜测解析；Schema 还要有版本和兼容策略，防止不同 Agent 升级后互相误解。

### 解析

考点不是禁止自然语言，而是区分协议字段与内容字段。结构化 Schema 提供可验证性、幂等和兼容性，自然语言作为载荷补充语义。

## 9. MCP Server 超时时，如何避免 Agent 重试造成重复写入？

#系统设计 #消息队列

### 知识点
- 分类：系统设计、消息队列
- 幂等键
- 任务ID
- 状态持久化
- 重试返回原结果

### 答案

写操作必须由调用方生成稳定的幂等键，并在所有重试中复用。MCP Server 或其后的业务服务要以幂等键建立唯一约束和状态记录：第一次执行成功后保存结果，重复请求直接返回同一结果；并发到达时只允许一个请求真正执行。

超时只表示调用方没收到结果，不代表服务端没执行。状态未知时应先查询任务状态，或让同一幂等键的重试安全接管，不能生成新键再次提交。对于不支持幂等的外部系统，还需要本地状态机、对账和人工补偿。

### 解析

核心是处理“结果未知”而非普通失败。端到端安全需要稳定幂等键、服务端原子去重、状态查询和补偿；仅在 Agent 侧记录任务 ID 不能阻止下游重复写入。
