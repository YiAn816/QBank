## 1. 加载预设提示词时可能遇到什么问题？

#提示词工程 #AI应用开发

### 知识点
- 分类：提示词工程、AI 应用开发
- 版本与环境不一致
- 模板变量缺失、类型错误和转义问题
- Token 超限与指令冲突
- 不可信输入注入和敏感信息泄露

### 答案

我会从版本、渲染、预算和安全四方面排查。首先确认当前环境加载了正确的 Prompt 版本；然后用强类型变量和模板测试检查缺失字段、错误转义及用户内容意外进入指令区；渲染后再计算 Token，防止动态内容让上下文超限。

另外要检查系统规则之间是否冲突，以及模板里有没有硬编码密钥或个人信息。Prompt 应该像代码一样做版本管理、评测和灰度发布，不能在生产环境里无记录地直接修改。

### 解析

考点是把 Prompt 当成可测试的软件资产。敏感内容治理不能只靠关键词表，还要结合输入边界、权限、数据脱敏和输出审核。

## 2. 多路检索结果融合后，还要不要做 Rerank？

#RAG #信息检索

### 知识点
- 分类：RAG、信息检索
- 融合解决多路候选合并
- Rerank 提升 Query 与候选的细粒度相关性
- 根据质量、延迟和成本决定

### 答案

通常值得做，但不是固定步骤。多路融合主要解决 BM25、向量检索等候选怎么合并，Rerank 则用更强的模型重新判断 Query 和候选文档的细粒度相关性。对于复杂问答或高质量要求场景，融合后 Rerank 往往能明显改善排序。

如果候选很少、查询简单或延迟预算很紧，也可以跳过或只对部分请求启用。最终要用 Recall@K、NDCG、答案正确率、延迟和成本评测，而不是把 Rerank 与 RAG 混为一个概念。

### 解析

RAG 是包含检索和生成的整体方法，不是排序模块。标准链路可以是 Query 处理、多路召回、融合去重、Rerank、上下文构建和生成。

## 3. 你怎么理解上下文？工具算不算上下文？

#大模型 #上下文工程

### 知识点
- 分类：大模型、上下文工程
- 上下文是当前模型调用可见的信息
- 工具 Schema、调用结果和错误可能进入上下文
- 外部系统状态不等于模型上下文

### 答案

上下文是一次模型调用中模型实际能够读取的信息，包括系统和开发者指令、用户输入、对话历史、检索证据、工具描述，以及已经放回消息中的工具结果。工具服务本身和它没有返回的数据不属于模型上下文。

工程上要区分真实业务状态与模型看到的状态：数据库里已经更新，不代表模型知道；工具返回进入上下文，也不代表内容可信。工具结果需要标注来源、时间和权限，并控制长度和提示词注入风险。

### 解析

考点是“模型可见性”。上下文不仅是聊天记录，还包括指令、工具 Schema 和外部证据；但外部世界的全部状态不会自动成为上下文。

## 4. 如何用 JSON Schema 校验工作流节点的输入输出？

#Python #数据校验 #工作流

### 知识点
- 分类：Python、数据校验、工作流
- 节点边界定义版本化 Schema
- Pydantic 或 JSON Schema 强校验
- 严格类型、额外字段和业务约束
- 错误隔离、重试和死信处理

### 答案

我会为每个节点定义版本化的输入输出模型，在节点执行前后都做校验。Python 中可以用 Pydantic 表达类型、必填字段、枚举、范围和跨字段规则，并配置是否拒绝额外字段；跨语言链路则发布标准 JSON Schema 和兼容策略。

校验失败时不能直接把错误数据交给下游。确定是模型格式问题时，可以在有限次数内按明确错误信息重新生成；无法安全修复的进入失败队列或人工处理，并保留原始输出和 Trace。金额、权限等业务语义仍需单独校验，Schema 正确不等于业务正确。

### 解析

“格式修复 Agent”不是默认兜底，因为它可能悄悄改变语义。完整方案要包括版本、严格校验、错误隔离、有限重试和业务规则。

## 5. 多场景并发调用 LoRA 时，如何降低显存占用和切换延迟？

#大模型推理 #LoRA

### 知识点
- 分类：大模型推理、LoRA
- 共享基座模型
- 热适配器常驻与按需加载
- LoRA 感知的 Continuous Batching
- 缓存、预取和租户公平性

### 答案

核心是只保留一份基座权重，把 LoRA 作为较小的独立制品管理。热门适配器常驻显存，冷门适配器按需加载并使用有容量上限的缓存；调度器根据近期流量预取，但不能无上限预加载。

推理层使用支持多 LoRA 的融合算子和 continuous batching，减少频繁切换与显存拷贝。同时监控命中率、加载耗时、吞吐、P95 首 Token 延迟和各租户公平性，在同适配器聚合效率与请求排队时间之间取舍。

### 解析

具体框架只是实现选择。面试重点是共享基座、适配器缓存、LoRA 感知调度、显存预算和尾延迟。

## 6. 上下文工程和记忆应该怎么设计？

#上下文工程 #记忆系统

### 知识点
- 分类：上下文工程、记忆系统
- 当前任务上下文与跨会话记忆分离
- 短期状态结构化
- 长期记忆可追溯、可过期和可删除

### 答案

上下文工程解决“这一次调用应该给模型看什么”，记忆解决“哪些信息值得跨轮次或跨会话保存”。当前任务的目标、约束、开放事项和工具状态适合结构化保存；近期对话保留原文加摘要；长期记忆只保存经过确认、稳定且有持续价值的信息。

记忆要带来源、时间、置信度、权限和有效期，并允许用户查看、纠正和删除。召回时按当前任务相关性和权限筛选，不能把所有记忆无差别塞回上下文。

### 解析

考点是写入、存储、召回和删除的完整生命周期。向量数据库只是检索手段，不等于记忆系统本身。

## 7. 更换模型后需要重写提示词吗？

#提示词工程 #模型迁移

### 知识点
- 分类：提示词工程、模型迁移
- 不一定重写，但必须重新评测
- 比较指令遵循、工具调用和结构化输出
- 灰度发布与回滚

### 答案

不一定要重写，但一定要重新评测。不同模型对指令层级、示例数量、工具 Schema、结构化输出和长上下文的表现不同，原 Prompt 能运行不代表质量和安全性没有变化。

我会在固定回归集上对比任务成功率、格式通过率、工具调用、拒答、安全、延迟和成本，再针对失败切片做最小修改。最后灰度发布并保留 Prompt 与模型的绑定版本，方便回滚。

### 解析

模型迁移是模型、Prompt、工具和推理参数的联合变更。直接全量重写会扩大变量，完全不改又可能隐藏兼容问题，控制变量评测最重要。

## 8. 为什么选择 LangChain，而不是完全原生实现？

#Python #LangChain #架构设计

### 知识点
- 分类：Python、LangChain、架构设计
- 模型与工具集成
- 预构建 Agent 抽象
- LangGraph 负责更底层的有状态编排
- 框架成本与锁定风险

### 答案

选择 LangChain 的主要价值是快速获得统一的模型接口、工具集成和常见 Agent 抽象，适合快速验证和标准工具调用流程。需要复杂的确定性与 Agent 混合流程、持久化、人工介入和恢复时，可以进一步使用底层的 LangGraph；它们不是同一个层级。

是否采用还要看团队和系统复杂度。简单链路用原生 SDK 可能更透明、依赖更少；框架适合减少重复集成，但要评估升级频率、调试复杂度、性能开销和供应商锁定，并把核心业务逻辑与框架 API 隔离。

### 解析

状态管理和持久编排更准确地说是 LangGraph 的能力，LangChain 提供更高层 Agent 与模型、工具集成。面试回答应说明收益、边界和选型条件。

## 9. 为什么要结合 BM25 和向量检索？

#信息检索 #RAG

### 知识点
- 分类：信息检索、RAG
- BM25 擅长精确词项
- 向量检索擅长语义匹配
- 分数校准或 RRF 融合
- 评测和查询分流

### 答案

BM25 对专有名词、编号、错误码和用户原词匹配很强，向量检索更擅长同义表达和语义相近内容，两者的失败模式互补。实际链路可以分别召回候选，再用分数校准、加权或 RRF 融合，最后去重和 Rerank。

融合比例要通过按查询类型切片的验证集调，不一定所有请求都用固定权重。关键词明确的查询可以偏 BM25，描述性问题可以提高语义召回权重。

### 解析

混合检索不是简单拼接两个列表。关键是分数不可比、重复结果、候选预算以及是否需要查询分流和精排。

## 10. 为什么要把 Prompts、模型和 MCP 工具调用模块抽象出来？

#AI应用开发 #架构设计 #MCP

### 知识点
- 分类：AI 应用开发、架构设计、MCP
- 业务逻辑与外部能力解耦
- 统一接口、错误和观测
- 版本、灰度、回滚与测试替身
- 权限与安全策略集中控制

### 答案

我会把 Prompt 渲染、模型调用、工具或 MCP 连接和业务状态机分层。业务层只依赖稳定接口，这样更换模型、Prompt 版本或工具实现时，不必改写整个流程，也方便使用 Mock 做单元测试。

公共调用层还可以统一处理超时、重试、幂等、限流、权限、日志、成本和审计。但抽象不能抹平重要语义，例如流式能力、事务性和工具副作用仍要显式暴露。

### 解析

考点是稳定边界和横切能力，而不是为了“封装”增加层数。好的抽象既减少耦合，也保留不同依赖的关键差异。

## 11. 系统提示词和用户输入应该怎么区分？

#提示词工程 #安全

### 知识点
- 分类：提示词工程、安全
- 系统指令定义职责、安全和业务边界
- 用户输入表达本次任务与数据
- 指令层级和不可信内容隔离
- 代码侧强制安全规则

### 答案

系统提示词用于定义 Agent 的职责、允许的能力、输出规范和安全边界；用户输入表达本次任务目标和数据。两者要通过消息角色和数据结构明确隔离，用户上传的网页、文档和工具结果也都属于不可信内容，不能覆盖高层规则。

不过提示词优先级不是安全边界。权限、参数校验和危险操作审批必须由代码和执行平台强制保证。超长用户输入可以分块、摘要或检索，但目标、约束和来源要保留。

### 解析

系统提示词负责“边界和规则”，不是“编辑”。完整回答需要覆盖角色分离、间接 Prompt Injection 和代码侧防护。

## 12. LoRA 微调时，如何用 Schema 和质量检查防止脏数据污染模型？

#Python #数据工程 #LoRA

### 知识点
- 分类：Python、数据工程、LoRA
- 版本化样本 Schema 和强类型校验
- 对话角色、工具 Schema 与序列约束
- 去重、隐私、授权和质量抽检
- 数据血缘与隔离评测集

### 答案

我会先定义版本化样本 Schema，明确消息角色、必填字段、工具调用格式、最大长度和允许值，并用 Pydantic 等工具在数据入口严格校验。格式通过后再做语义质量检查，包括重复与近重复、乱码、隐私和密钥、授权范围、答案与证据一致性，以及工具参数是否符合当前 Schema。

困惑度或分类模型只能作为辅助信号，不能低于某个阈值就一律删除。数据应保留来源和处理血缘，训练、验证和测试按用户或任务去重；异常样本进入隔离区人工抽检，而不是静默修复后直接训练。

### 解析

Schema 只能保证结构，不能保证事实和授权正确。可靠管道需要结构校验、语义质检、隐私治理、去重、血缘和评测隔离共同工作。

## 13. Python 中字典和列表有什么区别？

#Python #数据结构

### 知识点
- 分类：Python、数据结构
- 列表按位置组织，字典按键映射
- 两者都保留顺序，但语义不同
- 平均访问复杂度与内存取舍

### 答案

列表是按位置组织的可变序列，适合顺序遍历、按索引访问和保存重复元素；字典是键到值的映射，适合按可哈希键快速查找和表达有名称的字段。现代 Python 的字典保留插入顺序，但它的核心语义仍是映射，不应当作按位置访问的列表使用。

复杂度上，列表按索引访问平均是 O(1)，查找某个值通常是 O(n)；字典基于哈希表，按键查找平均是 O(1)，但占用更多内存，最坏情况也不能简单保证 O(1)。

### 解析

回答要结合数据访问方式选型，不只是背底层结构。还可以补充字典键必须可哈希，列表元素则没有这个限制。

## 14. Python 如何处理 CPU 密集型任务？

#Python #并发编程

### 知识点
- 分类：Python、并发编程
- 先分析和优化算法
- 默认 CPython 的 GIL 限制纯 Python 多线程并行
- 多进程、原生库、编译加速或外部服务
- free-threaded 构建需单独评估

### 答案

我会先做性能分析，确认瓶颈并优化算法和数据结构。对于默认启用 GIL 的 CPython，纯 Python 的 CPU 密集代码通常不能靠多线程充分利用多核，可以使用多进程；数值计算则优先使用会释放 GIL 的 NumPy 等原生库，也可以评估 Numba、C/C++ 扩展或独立计算服务。

CPython 3.13 起有 free-threaded 构建，但扩展兼容性、线程安全和实际性能仍需验证。多进程也有序列化、内存复制和进程间通信成本，任务粒度太小可能得不偿失。

### 解析

Numba 主要通过 JIT 编译加速适合的数值计算代码，不是所有 Python 代码都能获益。面试回答应从分析瓶颈开始，并说明各种并行或加速方案的适用条件与成本。

## 15. Python 如何处理 I/O 密集型任务？

#Python #并发编程

### 知识点
- 分类：Python、并发编程
- 线程池适合同步阻塞库
- asyncio 适合支持异步接口的大量并发 I/O
- 背压、超时、取消和连接池

### 答案

如果依赖是同步阻塞接口，我通常使用有上限的线程池；如果网络库和整个调用链都支持异步，并发量又很大，可以使用 asyncio。文件 I/O 是否真正异步取决于平台和库，很多时候仍由线程池完成，不能只加 `async` 关键字就获得收益。

工程上还要设置连接池、并发信号量、超时、取消、重试和背压，防止同时发起太多请求拖垮本机或下游。I/O 密集不等于完全不消耗 CPU，序列化、加密和数据处理仍可能成为瓶颈。

### 解析

选线程还是 asyncio 取决于依赖接口、并发规模和团队复杂度。重点是等待期间让出执行权，同时控制下游压力。

## 16. RAG 返回多少个 Chunk 比较合适？

#RAG #信息检索

### 知识点
- 分类：RAG、信息检索
- 没有固定 TopK
- 受问题、Chunk 粒度、模型窗口和 Rerank 影响
- 用评测选择工作点

### 答案

没有通用数字。合适的数量取决于问题需要几段证据、Chunk 大小、召回质量、是否经过 Rerank，以及模型上下文和延迟预算。简单事实题可能一两段就够，多跳问题则需要更多不同来源。

我会在验证集上同时观察证据 Recall、上下文精确率、答案正确率、引用准确率、延迟和成本，并允许根据查询动态决定 K。太少会漏证据，太多会加入噪声；“常见三到八个”只能作为初始实验点，不能当结论。

### 解析

应把 Chunk 数量当作系统超参数，通过评测和查询自适应选择。还要注意同一文档的重复块会占用候选预算。

## 17. RAG 训练中为什么要引入负样本？

#RAG #机器学习 #信息检索

### 知识点
- 分类：RAG、机器学习、信息检索
- 教会检索或排序模型区分相关与不相关
- 随机负样本与 Hard Negative
- 防止假负样本和数据泄漏

### 答案

训练检索器或 Rerank 模型时，只有正样本只能告诉模型“什么相关”，负样本才能帮助它学习决策边界。随机负样本通常太容易，更有价值的是 Hard Negative：表面相似、包含相同关键词，但不能回答当前问题的文档。

负样本也要控制质量。如果一段未被标注但实际能回答问题，把它当负样本会误导模型；从线上挖掘时还要防止时间泄漏和用户隐私。通常会混合随机负样本、批内负样本和经过筛选的 Hard Negative。

### 解析

负样本用于训练相关性，不是为了在生成阶段补充完整上下文。“小块召回、回到父文档取上下文”属于父子块检索或 Small-to-Big Retrieval，是另一个概念。

## 18. 检索链路中的 TopK 应该怎么设计？

#RAG #信息检索

### 知识点
- 分类：RAG、信息检索
- 分阶段设置候选规模
- 过滤和去重会消耗候选
- 动态 K、阈值和兜底
- 质量、延迟与成本评测

### 答案

TopK 要分阶段设计。每路粗召回可以取相对多的候选，融合后去重和权限过滤，再让 Rerank 处理较小集合，最终只选择能放进上下文的高质量证据。前一阶段还要为后续过滤预留余量。

K 不应完全固定，可以根据查询难度、分数分布、所需证据数量和延迟预算动态调整；低于质量阈值时宁可返回证据不足或走其他召回，也不要机械填满。最终通过离线检索与答案指标和线上实验选择工作点。

### 解析

TopK 是各阶段的资源预算，不是单一数字。回答应说明粗召回、融合、精排和生成阶段如何逐步缩小候选并设置降级策略。
