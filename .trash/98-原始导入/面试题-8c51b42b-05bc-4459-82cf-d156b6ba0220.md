## 题目 1

RAG 上线后用户经常搜不到正确答案，如何优化？

### 知识点

- 分类：系统设计、算法
- 数据层质量检查：去重、去噪、去除过期版本、纠正 OCR 错误、保留 Metadata（标题、章节、产品线、版本号）
- 切分策略：FAQ 按问答对、合同 按条款、表格 结构化、接口文档 按接口/函数，避免固定长度切块导致问题与答案分离
- 查询改写与混合检索：实体抽取、编号/日期/产品名等 Metadata filter，混合 BM25、关键词和向量检索
- 重排与评估：使用重排模型对候选进行排序，采用 Recall@K、MRR、NDCG、答案引用命中率等指标
- 日志打点：记录 Query、候选 Chunk、Rerank 分数、进入 Prompt 的上下文，便于定位正确答案丢失位置
- 错误分布分析：区分 FAQ、接口文档、长文档、短句 Query rewrite 的错误类型
- 业务上下文预填充：召回前补上用户角色、产品线、地区、时间范围，缩小匹配范围
- 高风险业务优先修复：金额、合同、合规等场景先做规则兜底，低风险场景再调召回质量
- 线上调优思路：先定位错误在哪一层，再按业务风险决定修复顺序，避免盲目调参

### 答案

RAG 召回不准要先按六层排查：①数据层检查文档是否有噪声、重复、过期、OCR 错误，并保留标题、章节、产品线、版本号等 Metadata；②切分层根据文档类型选择合适切分方式（FAQ 按问答对、合同 按条款、表格 结构化、接口文档 按接口/函数），避免固定长度把问题和答案切散；③查询改写和召回层要对 Query 做实体抽取、编号/日期/产品名等 Metadata filter，采用混合检索（向量+BM25+关键词）提升召回；④重排层使用重排模型对候选进行排序；⑤评估层使用 Recall@K、MRR、NDCG、答案引用命中率等指标量化；⑥日志记录 Query、候选 Chunk、Rerank 分数、进入 Prompt 的上下文，便于定位正确答案在哪一步丢失。同时要先在高风险场景（金额、合同、合规）做规则兜底，再在低风险场景调召回质量；从业务上下文预填充用户角色、产品线、地区、时间范围，缩小匹配范围；根据错误分布（FAQ、接口文档、长/短文档）做针对性优化。这样把召回不准的“玄学调参”变成系统化的工程排查。

### 解析

RAG 召回不准往往不是模型本身问题，而是检索链路中数据、切分、查询、召回、排序、评估任一环节出现断层，需分层排查并结合业务风险决定修复顺序。
