## 题目 1

工作流编排和 ReAct agent 有什么本质区别？

### 知识点

- 分类：系统设计
- 控制流显示定义 vs 动态决策
- 可预测、可审计、可回溯
- 生产系统优先选工作流编排

### 答案

工作流编排的控制流是显示定义的，节点路径和失败分支都写清楚；ReAct agent 的控制流由模型动态决策，灵活但不可控。生产环境中应优先选择工作流编排，以实现可预测、可审计和可回溯。

### 解析

工作流编排通过显示定义控制流实现可靠执行，而 Agent 依赖模型动态决策灵活性高但可控性差。

## 题目 2

工作流里的节点失败了怎么处理？

### 知识点

- 分类：系统设计
- 定义重试策略和超时
- 可重试节点自动重试
- 不可重试节点走补偿逻辑
- 全局超时阈值防止链路拖垮

### 答案

每个节点需定义重试策略和超时时间。对于可重试节点，加入重试键，失败后自动重试；对于不可重试节点，失败后执行补偿逻辑，如回滚已执行的上游节点。整个工作流需设置全局超时阈值，防止某个节点卡死导致整条链路崩溃。

### 解析

通过重试策略、补偿逻辑和全局超时确保工作流在节点失败时可靠处理。

## 题目 3

工作流里有些步骤可以并行怎么设计？

### 知识点

- 分类：系统设计、算法
- 识别无数据依赖节点
- 用 DAG 表示并行关系
- 设 barrier 等待所有并行节点完成
- 失败策略：等待完成或立即终止

### 答案

首先识别出无数据依赖的节点，使用 DAG（有向无环图）结构表示。并行节点同时触发，通过 barrier 机制等待所有并行节点完成后再进入下一步。对于并行节点中任意一个失败的情况，需设计策略决定是等待其他节点完成还是立即终止整个工作流。

### 解析

利用 DAG 和 barrier 实现并行执行，并通过失败策略保障一致性。

## 题目 4

工作流的状态怎么持久化？

### 知识点

- 分类：系统设计
- 节点输出写入持久化存储
- 带节点ID和执行时间戳
- 从最后成功节点恢复
- 状态存储支持事务

### 答案

每个节点执行完成后将输出写入持久化存储，并记录节点ID和执行时间戳。工作流重启时，从最后一个成功节点恢复，不重跑已完成的节点。状态存储需支持事务，以确保节点完成但状态未写入时不会导致重跑。

### 解析

通过持久化存储和时间戳实现工作流状态的可靠恢复和事务一致性。

## 题目 5

用户要实时看到工作流的执行进度怎么做？

### 知识点

- 分类：系统设计、计算机网络
- 使用 SSE 或 WebSocket 推送事件
- 前端订阅工作流ID对应事件流
- 节点状态变更实时推送
- 中间输出增量推送

### 答案

采用 SSE 或 WebSocket 协议推送节点状态变更事件。前端订阅工作流ID对应的事件流，每个节点开始、完成、失败时都推送一条事件。避免轮询以降低延迟和服务器压力。节点的中间输出可以增量推送，无需等待整个节点完成。

### 解析

通过 SSE/WebSocket 实现实时事件推送，提升用户体验和系统效率。

## 题目 6

工作流里有个节点需要人工审批怎么集成？

### 知识点

- 分类：系统设计
- 人工审批作为异步等待节点
- 触发后挂起工作流
- 通知审批人并等待回调
- 校验身份和工作流ID
- 挂起期间设置超时机制

### 答案

人工审批节点作为异步等待节点，触发后挂起工作流并发送通知给审批人。等待审批结果回调，回调时校验审批人身份和工作流ID。通过则继续执行，拒绝则走拒绝分支。在挂起期间设置超时机制，避免工作流无限等待。

### 解析

通过异步等待和回调机制集成人工审批流程，并保障超时可控。

## 题目 7

同一个工作流模板不同租户跑出来行为不一样怎么支持？

### 知识点

- 分类：系统设计
- 可变参数抽成配置项
- 按租户注入配置
- 节点属性租户级别覆盖
- 运行时实例化合并租户配置

### 答案

将工作流模板中的可变参数抽离为配置项，按租户进行注入。节点的 Prompt 模板、工具列表、超时时长等都支持租户级别覆盖。模板本身共用，在运行时实例化时合并租户配置，避免为每个租户复制模板导致维护成本爆炸。

### 解析

通过配置化和运行时合并实现多租户支持，降低维护复杂度。

## 题目 8

工作流版本升级了正在运行中的实例怎么处理？

### 知识点

- 分类：系统设计
- 运行中实例继续使用旧版本
- 新实例使用新版本
- 实例绑定版本ID
- 灰度升级按比例分配流量

### 答案

运行中的工作流实例继续使用启动时的版本运行，不能强制迁移到新版本。新实例才使用新版本。需在状态处理中给每个工作流实例绑定版本ID。进行灰度升级时，按流量比例分配新旧版本，观察错误率后再全量切换。

### 解析

通过版本绑定和灰度发布确保升级过程中系统稳定性和可追溯性。
