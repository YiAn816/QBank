## 1. Embedding 模型的原理、优缺点和评估方法是什么？

#Embedding #RAG

### 知识点
- 向量表示、对比学习、语义相似度、检索评测

### 答案

Embedding 模型把文本编码成稠密向量，让语义相关的内容在向量空间中更接近。它擅长处理同义表达和语义召回，但对精确数字、专有名词、否定关系和领域外文本可能不够敏感，所以生产中常与关键词检索结合。评估不能只看公开榜单，我会用业务标注集比较 Recall@K、MRR 或 nDCG，再看最终答案质量、延迟和成本，并按语言、领域和难例分桶。

### 解析

考察从原理到落地评估的完整理解。常见误区是把向量距离直接等同于事实相关性，或只评价最终生成而不单独测检索。

## 2. 常见问题太少时，如何主动补齐 RAG 评测集？

#RAG #评测

### 知识点
- 覆盖率、问题生成、聚类、人工审核

### 答案

我会先按业务意图、知识域、用户类型和失败类别统计覆盖率，找出空白区域。对已有文档可以基于章节、实体和业务流程生成候选问题，同时加入无答案、歧义、多跳和权限边界样本；生成结果必须由人工抽检或标注，不能直接当标准答案。上线后再对真实查询聚类，把新意图和高频失败持续补入滚动集，同时保留固定基准集防止回退。

### 解析

重点是覆盖结构而不是单纯扩大数量。模型生成样本适合发现候选，不能替代可靠的答案与证据标注。

## 3. 传统 RAG 的主要痛点有哪些？

#RAG #系统设计

### 知识点
- 数据治理、分块、召回、上下文、生成、评测

### 答案

我会把问题分成四层。数据层有文档脏、版本和权限不清；检索层有分块破坏语义、专有词或多跳问题召回不稳；生成层有上下文噪声、引用错位和超证据回答；工程层还有索引更新、延迟、成本和评测闭环。对应手段包括文档治理、混合检索、重排、父子块或上下文压缩、引用校验，以及版本化的离线和线上评测。

### 解析

考察是否理解 RAG 是完整系统，不是“向量库加模型”。回答应把问题与可验证的改进手段对应起来。

## 4. 新领域专有名词导致输出不稳定时，怎么快速修复？

#RAG #模型优化

### 知识点
- 术语表、检索增强、约束规则、回归测试

### 答案

如果问题是知识缺失或术语解释不一致，我会先做可回滚的知识热修：建立带版本的术语表，把标准名称、别名、定义和适用范围加入检索，并在生成时要求使用检索到的标准术语。对必须固定的输出字段再加词典校验或结构化规则。随后用包含新旧术语、歧义和反例的回归集验证。只有当问题是稳定的行为或表达模式，而不是动态知识，才考虑继续微调。

### 解析

重点是先判断知识问题还是行为问题。RAG 便于快速更新，但不能靠把整份词库无条件塞进 System Prompt。

## 5. RAG 的过程评测应该看哪些信号？

#RAG #评测

### 知识点
- 入库、召回、重排、上下文、生成、引用

### 答案

我会沿链路看：文档是否正确解析和入库；正确证据是否进入候选集；重排后是否进入最终上下文；上下文是否被截断或混入冲突版本；生成中的事实是否得到证据支持；引用是否真的指向对应片段。每一步都记录版本、分数、过滤原因和耗时。这样最终答案失败时，能区分知识缺失、检索失败、上下文组装问题还是模型理解问题。

### 解析

考察可诊断性。只看最终正确率，无法判断应该改文档、检索还是生成。

## 6. 如何设计 RAG 的失败分类体系？

#RAG #评测

### 知识点
- 可操作标签、责任环节、证据字段、层级分类

### 答案

分类要能直接指导修复。我通常先分为：知识库缺失或错误、解析与分块错误、权限或版本过滤错误、查询理解错误、召回缺失、重排错误、上下文组装错误、生成幻觉或理解错误、引用错误，以及评测误判。每个标签都绑定可观察证据和负责环节，并允许主因、次因两级标注。定期统计占比和趋势，避免标签越来越多却无法采取行动。

### 解析

重点是分类互斥性不必绝对，但必须可复现、可映射日志和改进动作。“回答不好”不是有用的失败类别。

## 7. 如何单独评估 RAG 的召回阶段？

#RAG #信息检索 #评测

### 知识点
- Recall@K、MRR、nDCG、证据覆盖、多跳

### 答案

先为每个问题标注能支撑答案的文档或片段，再计算 Recall@K；如果排序位置重要，再看 MRR 或 nDCG。多跳问题要评估所需证据是否同时被召回，而不是任意命中一个就算成功。我还会区分“知识库里没有证据”和“有证据但没召回”，并按查询类型、文档类型和权限场景分桶。最终还要检查召回片段是否真的包含答案，而不只是文档 ID 相同。

### 解析

这道题合并了两道召回评测题。只看 Top-1 命中或平均相似度，不能反映多证据和排序质量。

## 8. 企业知识库的数据应该如何治理和入库？

#RAG #数据治理

### 知识点
- 来源、解析、去重、版本、权限、血缘、索引

### 答案

企业 RAG 首先要做好文档治理。我会确认来源、负责人、有效期、版本和权限，清理重复、过期及互相冲突的材料；然后按类型解析正文、标题、表格、图片和附件，做结构化分块。每个块保留文档 ID、章节路径、版本、生效时间、权限标签、内容哈希和来源链接，再生成索引。入库过程要可增量、可重放、可删除，并用抽样和自动规则检查解析质量。

### 解析

这道题合并了“数据怎么入库”和“最先处理什么”。没有来源、版本和权限的数据，即使召回相似也不能可靠使用。

## 9. RAG 分块策略应该怎么设计？

#RAG #Chunking

### 知识点
- 文档结构、语义完整、异构内容、父子块、重叠

### 答案

我会先按文档结构和查询方式设计，而不是统一按字符数切。制度和技术文档优先沿标题、段落和列表边界；表格保留表头与行列关系，代码保留函数或类边界，扫描件还要保留页码与版面坐标。块太小会丢上下文，太大又会增加噪声，可以用适量 overlap，或者小块召回、父块生成。最后用不同块大小和策略做消融实验，看召回、答案、Token 和延迟的综合结果。

### 解析

这道题整合了多道分块与 Chunk Size 问题。重叠不是越大越好，重复内容会挤占上下文并造成分数偏置。

## 10. 文档分块不合理的 RAG 项目怎么修复？

#RAG #问题定位

### 知识点
- 失败样本、解析质量、重建索引、灰度验证

### 答案

我会从失败样本反查原文，确认问题来自边界错误、标题丢失、表格拆散、块大小不合适，还是 Embedding 与检索策略。修复时先版本化新的解析和分块规则，补全章节、来源、权限等元数据，再并行建立新索引，不能直接覆盖线上索引。用固定评测集和真实查询对比新旧召回与生成质量，小流量灰度后再切换，并保留回滚能力。

### 解析

重点是先定位再重建，而且索引变更要可比较、可回滚。盲目调整 Chunk Size 容易改善一类问题却损害另一类。

## 11. 检索到正确文档但引用了错误条款，怎么定位？

#RAG #调试

### 知识点
- 片段级追踪、版本冲突、上下文组装、引用映射

### 答案

我会沿候选召回、重排、最终上下文和生成引用四步检查。先看正确条款是否作为完整片段进入上下文，是否被旧版本或相似条款排到前面；再看引用 ID 与文本的映射是否在截断、去重或流式输出时错位。最后把答案中的事实逐条回查引用。修复可能是调整分块与重排、过滤无效版本，或让模型输出稳定的证据 ID 并由服务端渲染引用。

### 解析

考察文档命中与条款命中之间的区别。引用链接正确不代表引用内容真的支持答案。

## 12. 引用了正确文档但答案仍然错误，怎么优化？

#RAG #生成

### 知识点
- 上下文完整性、冲突证据、任务拆解、结构化抽取

### 答案

先确认片段是否包含回答所需的完整条件，而不是只有相似关键词；再检查上下文里是否混入冲突版本、否定条款或无关噪声。如果证据完整但模型理解错，我会把任务拆成事实抽取和答案组织两步，重要字段用结构化输出与规则校验，并明确“只依据证据、证据不足就拒答”。最后用这类失败样本做回归，比较 Prompt、模型和上下文策略的影响。

### 解析

重点是区分“文档正确”和“证据充分”。直接换更大模型之前，应先排查上下文及任务定义。

## 13. 如何把线上失败稳定回流成可复现的评测样本？

#RAG #评测 #数据工程

### 知识点
- 链路快照、脱敏、去重、标注、版本管理

### 答案

我会从用户点踩、重复追问、人工转接、低置信度和高频失败中采样，保存脱敏后的问题，以及模型、Prompt、索引、知识快照、召回片段和最终答案版本。样本先去重和聚类，再由标注人员补充期望答案、证据范围和失败类型；只保留有代表性且可授权使用的数据。固定失败样本进入回归集，新分布进入滚动集，并记录每次修复后是否真正通过。

### 解析

这道题合并了两道线上样本回流题。没有知识与链路版本的样本无法复现，只保存问答文本也无法定位原因。

## 14. 什么场景适合 GraphRAG，而不是普通 RAG？

#GraphRAG #RAG

### 知识点
- 多实体关系、跨文档、多跳、全局分析、成本

### 答案

当问题依赖明确的实体关系、跨文档多跳路径或全局主题结构时，我会考虑 GraphRAG，例如供应链关系、事件演化和组织关联分析。简单事实查询、FAQ 或单文档问答通常普通 RAG 更简单、更便宜。GraphRAG 还依赖可靠的实体抽取、消歧和图更新，不能因为关系复杂就说“必须使用”。实际可通过路由把关键词、向量、SQL 和图检索组合，并用业务评测证明收益大于构图成本。

### 解析

重点是适用条件和成本边界。图结构能帮助关系导航，但不会自动保证推理正确。

## 15. 什么是 RAG，它的工作流程是什么？

#RAG

### 知识点
- 检索增强生成、离线索引、在线检索、生成与引用

### 答案

RAG 是 Retrieval-Augmented Generation，也就是检索增强生成。离线阶段把外部知识解析、分块、加元数据并建立关键词或向量索引；在线阶段理解用户问题，按权限检索和重排相关证据，再把有限且可信的上下文交给模型生成答案，并返回引用。它能缓解知识过期和无依据生成，但效果取决于数据、检索和生成全链路，不能彻底消除幻觉。

### 解析

这道题合并了定义和流程题。回答不应把 RAG 限定为只使用向量数据库，也不能承诺完全解决幻觉。

## 16. 为什么 RAG 答案要带引用，如何保证回答有依据？

#RAG #可解释性

### 知识点
- 事实与证据绑定、来源展示、拒答、可验证性

### 答案

引用让用户能追溯来源，也让系统可以自动检查每个事实是否有证据。我会让模型输出事实与证据 ID 的对应关系，再由服务端根据 ID 渲染文档名、章节、版本和链接，避免模型编造 URL。生成前只提供授权且高相关的证据，生成后做事实级支持检查；关键证据缺失或来源冲突时明确拒答或提示不确定，而不是补全一个看似合理的答案。

### 解析

这道题合并了“为什么引用”和“如何有依据”。引用本身不是质量保证，必须验证引用内容是否真正支持对应结论。

## 17. 如何评测生成质量并发现 RAG 幻觉？

#RAG #幻觉 #评测

### 知识点
- 正确性、完整性、忠实度、引用准确、事实级核验

### 答案

我会同时评估答案是否正确、是否覆盖关键要点、是否忠实于上下文、引用是否准确，以及表达是否符合业务要求。检测幻觉时，把答案拆成可核验的事实声明，逐条判断引用证据是支持、矛盾还是未提及；证据中找不到的外部事实属于超证据生成。自动评分要用人工标注集校准，高风险样本必须人工复核，并区分模型幻觉与知识库本身错误。

### 解析

这道题合并了生成评测与幻觉发现。语句流畅、引用数量多，都不能替代事实级支持判断。

## 18. 如何减少 RAG 和通用 LLM 的幻觉？

#RAG #幻觉

### 知识点
- 可靠证据、工具、拒答、校验、人工审核

### 答案

我会先提高输入事实的可靠性：动态知识走 RAG，实时或精确数据走权威工具；检索结果做版本、权限和冲突过滤。Prompt 明确只根据证据回答，并提供证据不足时的拒答路径；输出后做结构、规则、事实与引用校验。高风险操作还要人工审批或使用确定性系统执行。幻觉只能降低，不能声称通过某一个 Prompt 或 RAG 就彻底消失。

### 解析

这道题合并了两道幻觉缓解题。防幻觉是多层工程控制，不应把模型自评当作唯一保障。

---

## 19. 时间衰减会怎样影响向量召回？

#向量检索 #RAG

### 知识点
- 相关性、新鲜度、过滤、重排、归一化

### 答案

时间衰减本质上是在相关性之外加入新鲜度偏好。它适合新闻、价格或状态类知识，但如果权重过大，会把新的弱相关内容排到旧的权威内容前面。通常先按生效时间过滤无效版本，再分别计算语义、关键词、权威性和时间特征，通过可校准的重排模型或规则组合。参数要按业务时效和离线评测调整，并监控旧但仍有效知识的召回损失。

### 解析

重点是时间不是普适排序目标。制度、历史事实与热点新闻对“新”的定义完全不同。

## 20. 如何处理同一制度的多个版本？

#RAG #版本控制

### 知识点
- 生效区间、当前版本、历史查询、版本过滤

### 答案

入库时要保存版本号、生效与失效时间、发布机构、替代关系和内容哈希。默认查询根据问题时间选择当前有效版本；用户问历史情况时，按指定时间检索对应版本，并在答案中明确标注。旧版本可以保留用于审计，但不应混入当前答案。遇到重叠生效或缺少替代关系时，应展示冲突并交由文档负责人处理。

### 解析

考察时态和版本治理。简单按更新时间排序可能把刚迁移的旧文档误当成最新制度。

## 21. 如何处理非常口语化的用户问题？

#RAG #Query理解

### 知识点
- 查询改写、别名、意图、混合检索、保留约束

### 答案

我会先识别意图、实体、时间和否定等关键约束，再结合业务别名、缩写和对话上下文生成规范查询，同时保留原问题一起检索。对于短或模糊问题，可以生成多个受控改写并用混合检索召回；如果关键条件缺失，就先追问。改写结果要可观测并用真实口语样本评测，防止模型在改写时改变用户意图。

### 解析

重点是改写用于补表达差异，不能擅自补事实。只做同义词扩展也难以处理歧义和上下文指代。

## 22. 怎么定位是检索问题还是生成问题？

#RAG #问题定位

### 知识点
- 证据存在性、候选集、最终上下文、生成

### 答案

我会按四个检查点定位：知识库里是否存在正确证据；证据是否进入候选召回；是否经过过滤和重排进入最终上下文；模型是否根据这份上下文答对。如果库里没有，是知识治理问题；没召回是分块、查询或检索问题；召回后没进入上下文是重排或组装问题；证据完整仍答错才主要是生成问题。每一步都要绑定同一请求的版本和日志。

### 解析

重点是比简单二分更细。正确文档出现在候选列表，不代表模型最终真正看到了完整证据。

---

## 23. 如何提高 RAG 的召回率？

#RAG #信息检索

### 知识点
- 数据、分块、混合检索、查询改写、多路召回

### 答案

我会先分析漏召回样本，而不是直接增大 TopK。数据侧补齐知识和元数据，分块侧保证答案片段完整；查询侧做别名、拼写和受控改写；检索侧组合 BM25、向量、字段过滤和必要的多路召回，再用重排控制噪声。优化要看 Recall@K、关键证据覆盖和最终答案，不然提高召回数量可能只是把更多无关文本塞进上下文。

### 解析

考察召回率和精度之间的权衡。盲目增大 TopK 会增加成本并降低生成质量。

## 24. RAG 如何做权限过滤并防止跨租户召回？

#RAG #安全 #多租户

### 知识点
- 可信租户上下文、ACL、检索前过滤、二次校验

### 答案

租户和用户身份必须来自认证链路，不能相信模型或客户端拼出的过滤条件。文档块入库时保存租户归属和 ACL，关键词检索、向量检索及父块展开都在候选产生前或检索引擎内部强制过滤；重排和生成只能看到授权结果。返回前再做资源级二次校验，并记录策略与权限版本。任何缺少身份上下文的请求默认拒绝，还要用跨租户负向测试持续验证。

### 解析

这道题合并了三道权限过滤题。先召回敏感内容再让模型删除，已经造成了数据暴露。

## 25. 召回结果互相冲突时怎么处理？

#RAG #数据治理

### 知识点
- 来源权威性、版本、生效时间、冲突展示

### 答案

我会按预先定义的权威来源、版本和生效时间判断，而不是让模型凭措辞选择。能确定替代关系时只使用有效版本；不同来源面向不同范围时，把适用条件一起带入。无法自动消解的冲突要明确展示各自来源和差异，降低回答置信度或转人工，并把冲突反馈给知识负责人。冲突策略本身也要版本化和审计。

### 解析

重点是冲突属于数据治理问题，不能仅靠相似度或“新文档优先”解决。

## 26. 知识库每天更新时，历史评测结果还能直接比较吗？

#RAG #评测 #版本控制

### 知识点
- 知识快照、索引版本、冻结集、并行对比

### 答案

不能直接比较，因为答案变化可能来自知识更新，也可能来自系统能力变化。每次评测要记录文档快照、解析、索引、模型和 Prompt 版本。比较算法能力时，让新旧系统运行在同一知识快照；评估知识更新效果时，固定系统版本，仅替换知识快照。报告分别展示固定集和随知识变化的滚动集，避免把正确的新答案误判为回退。

### 解析

考察实验变量控制。没有版本快照的历史分数，通常只能作趋势参考，不能作严格对照。

## 27. RAG 项目为什么会选择 Chroma？

#RAG #向量数据库

### 知识点
- 原型开发、部署成本、生产选型

### 答案

如果是本地实验、教学或小规模原型，我会考虑 Chroma，因为接口简单、启动快，便于验证 Embedding、分块和检索流程。是否用于生产，要结合当前版本实测数据规模、持久化、备份恢复、并发、过滤能力、可观测性和运维方式。选型结论不能只说“轻量好用”，还要与已有数据库、云服务或其他向量引擎在真实数据和 SLA 下对比。

### 解析

重点是给出有边界的选型理由。工具能力会随版本变化，生产决策应基于验证而非固定印象。

## 28. LLM 作为评审时评分不稳定，怎么处理？

#LLM #评测

### 知识点
- 评分标准、结构化证据、重复评测、人工校准

### 答案

我会固定评审模型、Prompt、采样参数和评分量表，让它先提取证据再按明确 rubric 输出结构化结果。对边界样本可以重复评审或引入独立评审，但不能把多数投票当作绝对真值。最重要的是用人工高质量标注集测一致性、偏差和阈值，定期复校；客观指标能用规则计算时，优先不用 LLM。评测版本变化后不能与旧分数无条件横比。

### 解析

考察 LLM-as-a-Judge 的可靠性边界。多模型投票可能共享偏差，仍需要人工基准。

## 29. LoRA 的 rank 应该怎么选？

#LoRA #微调

### 知识点
- 低秩维度、容量、显存、过拟合、验证集

### 答案

LoRA 的 rank 决定低秩更新的容量。rank 较小，参数和显存开销低，但可能表达不足；rank 较大，容量更强，同时训练成本和过拟合风险也会上升。我会从较小 rank 建立基线，在相同数据、训练步数和评测集上逐步比较任务质量、稳定性和资源消耗，并结合注入层、alpha 等参数一起调。没有一个适用于所有模型和任务的固定最优值。

### 解析

题目中的 RAG 与 LoRA 的 rank 是不同概念。重点是通过受控实验选择容量，而不是认为 rank 越大越好。

## 30. LoRA 能替代 Prompt 和 RAG 吗？

#LoRA #Prompt #RAG

### 知识点
- 指令控制、外部知识、行为适配、组合使用

### 答案

不能简单替代。Prompt 负责描述当前任务和约束，RAG 提供可更新、可引用的外部知识，LoRA 更适合学习稳定的行为、风格或领域模式。动态事实不适合只靠 LoRA 记忆，复杂行为也不一定能靠更长 Prompt 稳定实现。实际先判断瓶颈属于指令、知识还是能力，再单独建立基线，必要时组合使用并分别版本化。

### 解析

考察三种方法的职责边界。把同一问题同时用三种方法处理而不做消融，会增加成本且难以定位收益。

## 31. Lost in the Middle 问题怎么缓解？

#大模型 #RAG

### 知识点
- 长上下文、位置偏差、重排、压缩、任务拆解

### 答案

它指长上下文中位于中间的关键信息更容易被忽略。我的做法不是继续堆上下文，而是提高检索精度，把核心证据按相关性和逻辑顺序组织，必要时放在更显著的位置；对大量材料先分层检索、压缩或分步处理，再汇总答案。同时保留引用以验证有没有漏读。最终应在目标模型和真实上下文长度上评测，因为不同模型的表现并不完全相同。

### 解析

重点是控制上下文和信息组织。ReAct 不是专门解决位置偏差的保证方案，也不能替代检索与评测。

## 32. 重排和 HyDE 如何优化 RAG 准确率？

#RAG #检索优化

### 知识点
- Reranker、HyDE、候选集、适用边界

### 答案

重排是在较大的候选集上用更精细的模型重新计算查询与片段的相关性，把真正能回答问题的证据放到前面。HyDE 则先生成一个假设文档或答案表示，再用它检索，可能改善过短、抽象或表达差异大的问题。HyDE 也可能把错误假设带入检索，所以我会与原查询并行召回，而不是完全替换。两者都要在固定评测集上比较召回、最终答案、延迟和成本。

### 解析

考察方法原理和适用边界。重排不能找回候选集中不存在的证据，HyDE 也不是对所有查询都更好。

## 33. RAG 和模糊搜索有什么区别？

#RAG #信息检索

### 知识点
- 检索与生成、字符串近似、关键词、语义检索

### 答案

RAG 是“检索证据后让模型生成答案”的系统模式，检索部分可以使用关键词、向量、SQL 或图查询。模糊搜索通常指对字符串或关键词做近似匹配，它只是检索方法之一，不包含生成。名字、编号和精确术语往往关键词或模糊匹配更可靠；同义表达更适合语义检索。工程上常做混合检索，不应把 RAG 与向量搜索画等号。

### 解析

重点是概念层级不同。RAG 不一定更快或更准确，是否使用生成取决于用户任务。

## 34. RAG 为什么使用向量检索？

#RAG #向量检索

### 知识点
- 语义召回、表达差异、混合检索、局限

### 答案

向量检索能召回表达不同但语义相关的文本，适合自然语言问题和大规模非结构化知识。不过它对编号、精确数字、罕见术语和复杂过滤可能不如关键词或结构化查询，所以通常作为多路召回之一。实践中可以用小块做精确匹配，再展开包含它的父块给模型，兼顾召回精度与上下文完整性。是否引入要用真实数据证明收益。

### 解析

重点是向量检索的价值与局限。父子块检索是一种上下文策略，不是向量检索本身的必然组成。

## 35. Chunking、Hybrid Search 和 Reranking 各起什么作用？

#RAG #检索

### 知识点
- 知识单元、多路召回、精排、链路协同

### 答案

Chunking 决定索引和引用的知识单元，影响语义完整性与检索精度；Hybrid Search 用关键词、向量等多路方法扩大互补召回；Reranking 在候选集上做更精细的相关性排序，控制最终进入上下文的质量。三者是串联关系：分块不好会限制召回上限，召回没有正确证据时重排也救不回来。调优时应分别测每一段，再看端到端答案。

### 解析

考察 RAG 检索链路的职责划分。不能把三种技术当成互相替代的独立技巧。

## 36. RAG 全流程最容易在哪些环节出问题？

#RAG #工程实践

### 知识点
- 数据与检索上限、生成问题、分层诊断

### 答案

很多项目的主要瓶颈在数据治理、解析分块和召回，因为正确证据没有进入上下文时，模型再强也无法可靠回答。但不能断言永远只有这一环，权限过滤、版本冲突、重排、上下文组装和生成也会失败。我会用过程评测统计各类错误占比，再优先解决当前业务的最大瓶颈，而不是凭经验只调模型或 Chunk Size。

### 解析

重点是承认链路上限并用数据定位。面试中给出绝对答案，通常会忽略具体数据和场景。

## 37. RAG 线上效果怎么评估？

#RAG #线上评测

### 知识点
- 任务成功、用户反馈、质量、可靠性、成本

### 答案

线上我会分层看：业务层看任务完成率、问题解决率、追问率、人工转接和满意度；质量层抽样评估正确性、忠实度、引用和拒答；系统层看检索与生成延迟、错误率和成本。指标按场景、租户、版本和问题类型分桶，并通过 Trace 回放低分样本。用户点踩是重要信号但不等于准确标签，需要结合人工复核形成闭环。

### 解析

考察线上指标是否连接业务结果。只看召回命中率或点赞率，都会遗漏系统质量的重要部分。

## 38. Reranker 的原理和作用是什么？

#Reranker #RAG

### 知识点
- 双阶段检索、交叉编码、相关性排序、延迟

### 答案

第一阶段通常用 BM25 或双塔 Embedding 快速召回较多候选，Reranker 再对查询和每个候选做更精细的联合建模并输出相关性分数。常见的交叉编码器比向量相似度更能捕捉细粒度匹配，但计算更慢，所以只处理有限候选。选型时要比较 nDCG、关键证据进入上下文的比例、推理延迟和成本，并控制候选数与批处理。

### 解析

重点是双阶段检索中的职责划分：召回负责广度，重排负责精度；具体模型名称和实现要在回答中说明清楚。

## 39. RAG 评测闭环如何自动运行？

#RAG #评测 #CI

### 知识点
- 变更触发、版本化数据、分阶段指标、发布门禁

### 答案

我会把固定基准集和线上滚动集都做版本管理。当文档、解析、分块、Embedding、检索参数、重排、Prompt 或模型变化时，流水线自动构建候选索引并运行分阶段评测，输出召回、答案质量、引用、拒答、延迟和成本对比。确定性指标自动计算，LLM 评审用人工集校准；超过风险阈值就阻断发布，通过后再灰度。线上失败继续回流，形成可复现的新回归样本。

### 解析

重点是评测与变更、发布和线上反馈真正连接。只定时跑一份旧题集，不构成有效闭环。
