## 1. 工作流编排层为什么要持久化状态？

#工作流 #数据库

### 知识点
- 检查点、恢复、幂等、外部回调、审计

### 答案

因为工作流通常跨进程、跨实例并且持续时间长，只放在内存里经不起重启、迁移和网络故障。我会持久化工作流版本、节点状态、输入输出摘要、重试次数、幂等键和外部回调，状态变更使用事务或原子条件更新。恢复时先读取检查点，再查询不确定的外部动作是否已经生效，决定继续、补偿还是转人工，而不是从头盲目重放。

### 解析

重点是持久化服务于可恢复性和可追溯性。落库本身不够，还要设计幂等与不确定状态处理。

## 2. Agent 生成的工具参数错误怎么拦截？

#Agent #数据校验

### 知识点
- Schema、业务规则、权限、风险控制

### 答案

我会分三层校验：先用 JSON Schema 或强类型模型校验结构、类型和枚举；再用业务规则校验金额、时间、门店和资源状态；最后根据可信身份检查用户与租户权限。校验失败时返回明确的机器可读错误，让模型修正一次或请用户澄清。高风险写操作还要做范围限制、预览和二次确认，不能因为格式合法就直接执行。

### 解析

考察结构正确与业务正确的区别。无条件让模型反复重试，可能把错误升级为事故。

## 3. 用户要求删除记忆时，怎样保证全链路删干净？

#隐私 #数据库 #Agent记忆

### 知识点
- 数据血缘、派生数据、异步删除、备份与审计

### 答案

首先确认删除范围，是单条事实、某类偏好还是全部记忆。系统通过稳定的数据 ID 和血缘关系，删除或失效主库、向量索引、缓存、摘要画像、离线特征、任务引用和获准回流的评测样本；删除任务持久化状态，失败可重试并告警，还要阻止异步队列把旧数据写回来。审计只记录操作和结果，不保留敏感原文。备份和法定留存数据按适用政策隔离，到期清除，且不得再进入在线处理。

### 解析

这道题合并了四道记忆删除题。跨存储删除通常是可追踪的异步工作流，不应承诺靠一次分布式事务实现绝对同步物理擦除。

## 4. 导出任务和离线中间表如何实现租户隔离？

#多租户 #数据安全

### 知识点
- 数据血缘、租户快照、最小权限、审计与过期

### 答案

所有中间数据集、对象和任务都带可信租户归属与来源血缘，生成、消费、导出各阶段都重新校验。导出服务使用租户范围内的快照和最小权限账号，禁止任意扫描全局明细；结果文件按租户命名空间加密存储，使用短期下载链接并自动过期。任务还要限制行数、频率和敏感字段，审计谁在何时导出了什么范围，并用跨租户负向测试做发布门禁。

### 解析

重点是旁路和离线链路也必须执行同样的隔离策略，不能依赖开发人员手工加条件。

## 5. 端云两侧同时修改用户状态时，冲突怎么收敛？

#同步 #数据一致性

### 知识点
- 版本向量、字段合并、冲突记录、用户确认

### 答案

我会先按字段定义合并语义。可交换的集合或计数可以用确定性合并或 CRDT；不可交换的事实字段带版本、设备和时间，使用乐观并发控制，不能只靠客户端时间做最后写入胜出。偏好或推断互相冲突时保留来源与分支，无法自动裁决就让用户确认。同步协议还要支持去重、重放和删除标记，避免离线旧数据复活。

### 解析

考察冲突解决策略。统一使用“最后写入胜出”简单，但会受时钟偏差影响并静默丢失数据。

## 6. 多个工具串联时，如何保证失败后可恢复？

#Saga #分布式事务

### 知识点
- 状态机、幂等、补偿、不确定状态

### 答案

跨系统调用通常不能依赖一个本地事务，我会使用 Saga 或持久化状态机，把流程拆成边界清晰的步骤。每步有幂等键、成功判定、超时和补偿动作，状态转换持久化并通过 Outbox 等方式可靠投递事件。失败时按已完成步骤逆向补偿；补偿不可用或结果不确定时暂停转人工。回滚是业务补偿，不等于数据库恢复到从未发生过。

### 解析

重点是处理半成功与不可逆副作用。声称所有外部调用都能原子回滚通常不现实。

## 7. 多模态证据如何存储和对齐？

#多模态 #数据模型

### 知识点
- 时间戳、空间坐标、来源、版本、证据引用

### 答案

我会给每份原始媒体分配不可变 ID，文本转写绑定时间区间，OCR 绑定页码或图像坐标，模型结论再引用这些证据 ID。记录解析模型、版本、置信度和内容哈希，使用户能从结论跳回原视频、音频或图片区域。媒体重新处理时生成新版本，不覆盖旧证据；高风险判断由规则或人工复核。

### 解析

重点是跨模态证据可追溯、可复核。只保存抽取文本会丢失空间、时间和来源关系。

## 8. 多设备同时修改同一条记忆，如何避免旧写入覆盖新事实？

#并发控制 #数据库

### 知识点
- 版本号、CAS、冲突合并、事件时间

### 答案

读取记忆时返回版本号，更新时用 `WHERE id=? AND version=?` 做 CAS；受影响行数为零就说明发生冲突，需要重新读取。能确定合并语义的字段按规则合并，事实冲突则保留来源、事件时间和多个候选，必要时请用户确认。客户端重试带幂等键，服务端时间与设备时间分开记录，不能让一台时钟错误的设备覆盖新事实。

### 解析

考察乐观并发控制与业务冲突处理。CAS 能发现覆盖，但不能替系统决定哪个事实正确。

## 9. 多租户系统如何防止串数据？

#多租户 #数据库 #安全

### 知识点
- 可信租户上下文、全链路过滤、资源隔离、默认拒绝

### 答案

网关根据认证结果生成可信租户上下文，并强制传到数据库、缓存、向量索引、对象存储和消息任务。共享表中的记录带租户 ID，查询构造器和数据访问层自动加过滤；缓存键、文件路径和队列消息也包含租户维度。高安全或大体量租户可以使用独立库、索引或部署。任何环节缺少租户上下文都默认拒绝，并通过审计和跨租户负向测试验证。

### 解析

这道题合并了三道租户隔离总览题。只在关系表加 `tenant_id`，无法覆盖缓存、异步和分析链路。

## 10. 多租户日志应该怎么做？

#日志 #多租户 #安全

### 知识点
- 租户标签、脱敏、访问控制、审计

### 答案

日志要带由服务端注入的租户和 Trace 标识，便于隔离查询和排障，但敏感字段、Prompt、工具参数和凭证必须最小化记录并脱敏。日志平台本身实施租户与运维角色权限，跨租户查询需要审批和审计。保留周期按数据等级配置，导出和调试副本同样受控，不能为了排障默认记录完整业务数据。

### 解析

考察可观测性与隐私的平衡。日志平台经常成为隔离遗漏点，也不能把租户 ID 当作秘密替代权限控制。

## 11. 高并发工作流如何保证状态一致性，并处理缓存不一致？

#状态机 #MySQL #缓存

### 知识点
- 合法状态转换、乐观锁、数据库真相、缓存失效

### 答案

我会让数据库保存权威状态，每次转换用“当前状态 + 版本号”作为条件原子更新，同时校验状态机允许的边；失败则重新读取，而不是覆盖。状态变更与事件投递可用事务 Outbox 保证一致，消费者按事件 ID 幂等。缓存只用于展示或加速读取，采用更新数据库后失效缓存，并允许短暂不一致；关键决策直接读权威状态。如果业务要求更强一致，就不要依赖本地缓存。

### 解析

这道题合并了状态缓存和高并发流转。Redis `SET` 本身不能保证数据库与工作流状态原子一致。

## 12. 共享表模式下，租户 ID 应该如何参与索引设计？

#MySQL #多租户 #索引

### 知识点
- 联合索引、选择性、查询模式、安全边界

### 答案

大多数按租户查询的共享表，应让联合索引包含租户 ID，并根据等值、范围、排序和选择性决定列顺序。例如常见查询可设计 `(tenant_id, status, created_at)`，减少跨租户扫描。但索引只是性能工具，不是权限边界；真正的隔离仍由可信上下文和强制查询条件保证。全局管理查询、唯一约束和超大租户还要单独设计，并用 `EXPLAIN ANALYZE` 验证真实计划。

### 解析

这道题合并了两道索引隔离题。机械地把租户 ID 放在所有索引首列可能影响其他查询，且不能替代授权控制。

## 13. 会议纪要如何支持追溯和纠错？

#版本控制 #数据库

### 知识点
- 证据绑定、版本、差异、确认状态

### 答案

每条结论绑定转写片段、音频时间、说话人和来源文件，并记录 ASR 与生成模型版本。用户修改时创建新版本，保留差异、修改者和原因，不覆盖历史；后续任务只消费明确标记为已确认的最新版本。原始音频、转写和纪要使用稳定 ID 关联，权限和保留策略保持一致。

### 解析

重点是结论到原始证据的链路和不可变版本。只保存最终文本无法解释错误来自转写还是总结。

## 14. 记忆越来越多时，什么时候归档或删除？

#数据生命周期 #Agent记忆

### 知识点
- 保留策略、价值、时效、合规、用户控制

### 答案

我会先按记忆类型定义保留规则，而不是统一按相似度淘汰。短期上下文到期自动删除，长期偏好结合最近使用、置信度和用户确认决定保留；过期事实先失效，必要时归档。涉及合同、承诺或合规的数据按法定期限处理，用户删除请求优先执行适用政策。归档数据默认不参与召回，并定期验证删除与恢复流程。

### 解析

重点是生命周期由用途和规则决定。访问少不代表可以删，访问多也不代表应永久保留。

## 15. 如何从架构上防止查询漏写租户条件？

#多租户 #MySQL

### 知识点
- 数据访问层、受限账号、静态检查、测试

### 答案

业务代码不应直接获得裸表查询能力。我会在仓储层或查询构造器中强制注入可信租户条件，数据库账号按用途限制权限，并为后台全局任务使用独立、可审计的接口。CI 做静态规则检查和跨租户集成测试，运行时记录无租户上下文的访问并直接拒绝。MySQL 没有通用的原生行级安全可以自动兜底，因此应用层约束和测试尤其重要。

### 解析

重点是用机制减少人为遗漏。代码审查或命名约定不能成为唯一防线。

## 16. 企业知识库 RAG 与普通问答 RAG 有什么区别？

#企业RAG #数据治理

### 知识点
- 权限、版本、结构化数据、SLA、审计

### 答案

企业场景除了回答质量，更强调身份权限、文档版本、生效时间、引用审计、删除和更新 SLA。知识来源不仅是文本，还可能包含数据库、工单和实时业务 API，因此需要路由到结构化查询，不能全部向量化。上线还要有评测门禁、故障降级、成本控制和责任人。普通演示型问答往往只验证“能否回答”，企业系统则要证明答案可控、可追溯且不越权。

### 解析

考察生产级 RAG 的治理要求，而不是某个特定公司的业务细节。

## 17. 企业 RAG 为什么常用混合检索？

#RAG #BM25 #向量检索

### 知识点
- 精确匹配、语义匹配、融合、重排

### 答案

企业知识里既有自然语言同义表达，也有产品名、错误码、条款号和数字等精确词。向量检索擅长语义，BM25 等关键词方法更擅长稀有词和精确匹配，所以我会让两路在同一权限范围内召回，做去重和分数融合，再用 Reranker 精排。是否混合以及权重多少，需要在业务评测集上验证。

### 解析

重点是两类检索互补。直接相加不同系统的原始分数通常不可比，需要归一化或排名融合。

## 18. 如何评估企业 RAG 的权限隔离是否可靠？

#RAG #安全测试

### 知识点
- 越权负向样本、身份变化、泄露率、审计

### 答案

我会构造租户、部门、角色、历史权限和相似文档之间的越权测试，覆盖关键词、向量、父块展开、缓存和引用下载。预期无权内容在候选召回阶段就不可见，同时检查响应、日志和 Trace 是否泄露标题或片段。权限变更、离职转岗和索引更新后继续回归，任何泄露都作为发布阻断。线上只记录必要的身份、策略版本和资源 ID 供审计。

### 解析

权限测试需要专门的负向样本。答案没有泄露，不代表候选列表和日志中没有暴露敏感内容。

## 19. RAG 权限应该放在哪一层？

#RAG #权限

### 知识点
- 入库标签、查询过滤、资源复核、权限变更

### 答案

权限不是只放一层。入库时把资源归属、角色、密级和生效信息作为可更新元数据；查询时根据认证身份生成策略，在检索引擎内过滤；父块展开、引用下载和工具读取时再次做资源级授权。模型永远只看到已授权内容。权限变化后要及时更新元数据、失效缓存，并用策略版本保证旧结果不会继续使用。

### 解析

重点是多层防御。给块打标签但查询不强制过滤，或者只在输出阶段脱敏，都不可靠。

## 20. 工具返回成功，但业务结果不符合预期，怎么办？

#Agent #业务一致性

### 知识点
- 技术成功、业务后置条件、二次查询、补偿

### 答案

接口成功只代表请求被接受或处理完成，不等于业务目标达成。我会为每个动作定义可验证的后置条件，例如订单状态、库存锁定和退款流水，再通过权威查询接口确认。未满足时先判断异步处理中、部分成功还是业务拒绝，然后等待、补偿或转人工；不能重复执行写操作。工具协议应分别返回调用状态、业务状态和可查询的任务 ID。

### 解析

考察技术状态与业务状态的分离。只检查 HTTP 200 或 `success=true` 容易误报成功。

## 21. 主状态库丢数据但外部流程已执行一半，怎么恢复？

#灾难恢复 #分布式系统

### 知识点
- 停止重放、幂等键、外部事实、状态重建

### 答案

先冻结受影响流程，避免自动重试扩大影响。根据幂等键、Outbox、审计日志、外部回执和业务查询接口，逐步确认哪些动作已生效，重建工作流检查点；无法确认的标记为不确定并转人工。恢复后从第一个未完成且可安全执行的步骤继续，所有写入仍使用原幂等键。事后还要修复备份、日志和恢复演练，不能把外部系统当成临时数据库长期依赖。

### 解析

重点是以外部业务事实重建状态，不能直接从旧检查点全量重放。

## 22. Agent 推荐超卖商品并引导下单，如何处理？

#电商 #库存 #Agent

### 知识点
- 止损、权威库存、缓存、下单校验

### 答案

先停止展示或推荐受影响商品，并核对订单与用户影响。排查商品检索、库存缓存、推荐快照和下单接口的版本与时间，确认是过期数据还是库存扣减并发问题。长期设计上，模型只能展示权威商品服务返回的状态；推荐结果可缓存，但进入购物车和提交订单时必须由交易系统重新校验并原子预占或扣减库存，失败就明确告知用户。

### 解析

重点是库存事实由交易系统保证。关闭召回只能临时止损，不能替代下单链路的并发控制。

## 23. 如何处理 AI 导购本地缓存与后台购物车的一致性？

#缓存 #电商 #一致性

### 知识点
- 权威数据源、版本、失效、读己之写

### 答案

## 28. 什么是覆盖索引，它如何优化查询？

#MySQL #索引

### 知识点
- 所需列、回表、二级索引、查询模式

### 答案

### 解析

## 29. 什么是 MySQL 间隙锁？

#MySQL #锁

### 知识点
- Gap Lock、Next-Key Lock、索引范围、可重复读

### 答案

间隙锁锁住索引记录之间的区间，阻止其他事务向该范围插入记录；它常与记录锁组合成临键锁。InnoDB 在可重复读下的锁定读、更新或删除范围时，可能使用间隙或临键锁来避免幻影和保证复制等语义。具体锁范围取决于索引和查询条件，唯一索引等值命中通常不需要锁前后间隙。排查时应结合执行计划和锁监控，不能只看 SQL 表面范围。

### 解析

重点是锁作用于索引范围，不是抽象的“表中空白”。普通一致性快照读与锁定读的行为也不同。

## 41. MySQL 的事务隔离级别和 MVCC 怎么理解？

#MySQL #事务 #MVCC

### 知识点
- RU、RC、RR、Serializable、Read View、当前读

### 答案

SQL 标准常见四级是读未提交、读已提交、可重复读和串行化，隔离越强通常并发代价越高。InnoDB 默认使用可重复读。MVCC 通过隐藏版本信息、Undo 版本链和 Read View，让普通一致性读在不阻塞写入的情况下读取可见版本；读已提交通常每条语句创建新 Read View，可重复读通常在事务首次一致性读时建立并复用。更新、删除和 `SELECT ... FOR UPDATE` 属于当前读，还要依赖记录锁和临键锁。

### 解析

这道题合并了三道隔离级别题。最左前缀属于索引，不属于事务隔离；MVCC 也不能替代所有锁。

## 43. MySQL 为什么常用 B+ 树索引？

### 知识点
- 高扇出、低树高、范围扫描、聚簇与二级索引

### 答案

### 解析

重点是磁盘页、树高和有序叶子。不能笼统地说所有 B+ 树叶子都保存完整数据行。

## 44. 如何用 MySQL 实现分布式锁？

#MySQL #分布式锁

### 知识点
- 唯一约束、锁记录、租约、所有者、fencing token

### 答案

一种做法是建立锁表，以资源 ID 建唯一约束，事务内插入或条件更新锁记录，保存 owner、租约到期时间和单调递增的 fencing token；释放时只允许当前 owner 删除。租约解决进程崩溃，但要处理数据库时间、续租和暂停过久，资源服务还应校验 fencing token，拒绝旧持有者的迟到写入。MySQL 也有命名锁能力，但它绑定连接且有适用限制。高频锁要评估数据库热点和故障边界，必要时选择更合适的协调系统。

### 解析

重点是“获得锁”之外的失效与旧持有者问题。只有过期时间而没有 fencing，仍可能发生两个客户端同时操作资源。
