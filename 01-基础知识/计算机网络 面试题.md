## 1. 从输入 URL 到页面返回，网络流程是什么？

#计算机网络 #HTTP

### 知识点
- DNS、连接建立、TLS、HTTP、缓存、浏览器渲染

### 答案

我会按链路来回答。浏览器先解析 URL，检查本地缓存和 Service Worker；需要访问网络时，通过 DNS 获得目标地址，再根据协议建立连接：HTTP/1.1 和 HTTP/2 通常基于 TCP 并进行 TLS 握手，HTTP/3 则基于 QUIC。随后请求可能经过 CDN、负载均衡和网关到达服务端。服务端完成鉴权、业务处理和数据访问后返回响应，浏览器再解析 HTML、加载子资源、构建 DOM 和 CSSOM，最后布局、绘制并合成页面。实际排查时，我会用性能时间线区分 DNS、连接、首字节和渲染分别慢在哪里。

### 解析

考察端到端网络链路。常见误区是把所有 HTTP 都说成基于 TCP，或者只讲到服务端返回而忽略缓存、代理和浏览器渲染。

## 2. 登录态和权限应该怎么处理？

#安全 #HTTP #Agent

### 知识点
- 认证、授权、会话、令牌过期、敏感操作再确认

### 答案

登录态应该由可信的身份与会话系统管理，不能依赖模型记忆。入口先验证 Cookie、Session 或 Token，再根据用户、租户和资源做授权；令牌要有明确有效期、可撤销，并使用安全存储和传输。Agent 执行敏感操作前还要重新检查权限，必要时要求用户二次确认。长任务中如果凭证过期，应暂停并重新认证，而不是绕过校验继续执行。

### 解析

重点是区分认证和授权，并说明权限检查必须落在服务端及工具端。模型上下文只能携带经过验证的身份信息，不能成为身份事实来源。

## 3. 多个 Agent 共享状态时，最容易踩什么坑？

#Agent #分布式系统

### 知识点
- 并发写、版本冲突、幂等、事件日志

### 答案

最常见的问题是多个 Agent 同时修改同一任务，发生覆盖、重复执行或状态回退。我会把只读上下文和可变任务状态分开，对可变状态使用版本号或乐观锁，并让写操作带幂等键。重要变更以追加事件记录操作者、时间和因果关系；发现版本不一致时重新读取并合并，而不是直接覆盖。这样既能避免并发冲突，也方便事故追溯和重放。

### 解析

考察共享状态的一致性设计。只说“加锁”不够，还要覆盖跨进程并发、重复消息、失败重试和审计需求。

## 4. 多团队共同维护服务时，Agent 如何确定处置责任人？

#运维 #Agent

### 知识点
- 服务目录、值班表、升级策略、事故指挥

### 答案

我会让 Agent 依据服务目录中的 owner、当前值班表和依赖关系来确定责任人，而不是从日志文本里猜。告警先映射到受影响组件，再查主责团队和升级链；跨团队或归属不清时，升级到统一事故指挥渠道，由事故负责人协调。服务目录、值班信息和联系方式都要定期校验，并记录通知是否送达和是否被接手。

### 解析

重点是责任信息必须来自可维护的权威系统，同时保留无法自动判断时的人工升级路径。

## 5. 多租户 Agent 系统如何建立可信的租户身份？

#安全 #多租户 #Agent

### 知识点
- 身份边界、租户上下文、服务端注入、全链路传播

### 答案

第一步是锁住身份入口。网关根据已验证的用户凭证解析其租户归属，生成可信租户上下文，再把它传到检索、缓存、任务队列和工具调用链路。租户 ID 不能直接相信客户端或模型参数；客户端即使传了，也只能作为待校验信息。任何内部请求缺少租户上下文都应默认拒绝，服务和工具还要再次校验用户是否有权访问目标资源。

### 解析

这道题合并了“先隔离哪一层”和“租户 ID 由谁写入”。核心是租户身份由服务端认证链路产生，且全链路不可丢失、不可被模型覆盖。

## 6. 多租户隔离怎么测试？

#测试 #安全 #多租户

### 知识点
- 负向测试、跨租户访问、异步链路、发布门禁

### 答案

我会重点做负向测试：让租户 A 使用自己或伪造的身份，尝试访问租户 B 的文档、向量、缓存、会话、任务和工具凭证，预期都必须失败。还要覆盖分页、导出、批量接口、异步消息、失败重试、缓存命中和日志查询，因为这些地方容易漏传租户条件。测试要同时检查响应、存储和审计日志，并进入 CI 和发布门禁；重要隔离策略还需要定期做渗透与回归测试。

### 解析

考察是否能覆盖业务表之外的中间层和异步链路。性能压测不能替代越权负向测试。

## 7. 多租户场景下，工具调用凭证怎么管理？

#安全 #多租户 #Agent

### 知识点
- 短期凭证、最小权限、密钥托管、二次校验

### 答案

长期密钥不能放进 Prompt、日志或模型上下文。我会由凭证服务或工具网关按请求签发短期凭证，绑定租户、用户、工具、权限范围和过期时间，并尽量使用一次性或可撤销令牌。工具端不能只相信网关，还要校验签名、作用域和目标资源。密钥统一放在密钥管理系统中轮换，日志只记录凭证标识和授权结果，不记录明文秘密。

### 解析

重点是避免凭证泄露和混用。仅把长期密钥加密存储仍不够，还需要最小权限、短时有效和工具端校验。

## 8. 多租户 Agent 系统最容易在哪些地方串数据？

#安全 #多租户 #Agent

### 知识点
- 检索、缓存、记忆、异步任务、日志与评测

### 答案

高风险位置包括向量检索过滤、缓存键、会话记忆、工具结果、异步任务、文件存储、日志平台和离线评测数据。我的原则是所有资源都带不可伪造的租户归属，查询和缓存键强制包含租户维度，消息消费端重新校验上下文。共享基础设施还要配置访问策略和审计；一旦缺少租户标识就拒绝处理，而不是默认落到公共空间。

### 解析

考察全链路隔离意识。只在主业务表加 `tenant_id`，无法防止缓存、检索或异步任务发生数据串用。

## 9. 如何设计基于证据链的根因定位？

#可观测性 #运维 #Agent

### 知识点
- 指标、日志、追踪、基线、变更事件、证据链

### 答案

我会从告警对应的服务、时间窗和异常指标出发，沿 Trace 向上下游展开，再关联同一时间段的日志、资源指标和发布、配置、流量等变更事件。判断根因时不仅看相关性，还要和正常基线、相邻实例及对照时间段比较，并检查故障传播顺序。Agent 输出应区分事实、推断和待验证项，给出可点击的证据和验证步骤；证据不足时只能报告候选原因，不能直接下结论。

### 解析

这道题合并了根因链路和日志分析。重点不是生成一段摘要，而是建立时间、调用关系和变更之间可验证的因果证据。

## 10. Agent 或 MCP 工具调用链路如何做可观测性？

#MCP #可观测性 #Agent

### 知识点
- Trace、调用标识、版本、参数脱敏、分层指标

### 答案

我会给一次 Agent 运行分配 `trace_id`，每次模型和工具调用分配独立的 `span_id` 与 `call_id`，记录模型、Prompt、MCP 服务和工具版本，以及调用状态、耗时、重试和错误类型。参数、结果只保留必要摘要并做脱敏，高风险操作还要记录授权与确认信息。指标按租户、场景、工具和错误类型拆分，关注成功率、延迟分位数、超时率和重试率，并让日志、指标、Trace 能通过同一标识互相跳转。

### 解析

这道题合并了普通工具与 MCP 工具的观测。常见误区是只统计整体成功率，或者为了排障把敏感参数完整写入日志。

## 11. 工具调用失败时应该怎么重试？

#可靠性 #Agent

### 知识点
- 错误分类、指数退避、幂等键、重试预算

### 答案

我会先分类：连接中断、超时和限流这类瞬时错误，可以在重试预算内做指数退避并加随机抖动；参数错误要修正参数或请用户澄清；权限和确定性的业务错误不应重试。写操作必须先确认接口幂等，使用幂等键或先查询执行状态，避免超时后重复扣款、发消息。达到上限后进入降级、人工处理或死信队列，并保留最后错误和调用链。

### 解析

重点是“可重试性”由错误语义和操作幂等性共同决定。无差别立即重试会放大下游故障。

## 12. 流式输出在后端怎么设计？

#SSE #WebSocket #后端

### 知识点
- 流协议、背压、取消、断线恢复、错误事件

### 答案

如果主要是服务端持续向浏览器推送文本，我通常选 SSE；需要双向低延迟交互时再选 WebSocket。后端把一次生成拆成开始、增量、完成和错误事件，附带任务 ID 与序号，并定期发送心跳。链路要处理客户端取消、连接断开、代理缓冲、超时和慢客户端背压；能恢复的场景可以用事件 ID 续传，不能恢复则明确让客户端重新发起。流结束后还要可靠保存最终状态，不能把“连接断开”当成任务成功。

### 解析

考察的不只是如何逐 Token 返回，还包括连接生命周期和任务状态一致性。SSE 是单向推送，取消通常通过断开连接或额外接口完成。

## 13. 为什么要单独设计模型网关？

#系统设计 #大模型

### 知识点
- 供应商适配、路由、限流、成本、审计与降级

### 答案

模型网关把业务与不同模型供应商的协议差异隔开，统一做鉴权、配额、限流、路由、超时、重试、内容安全、成本统计和可观测性。这样业务可以按场景选择模型，也更容易灰度和故障切换。不过网关不能抹平所有模型能力差异，流式响应、工具调用和上下文限制仍要显式建模；同时要做高可用，避免网关自己成为单点和性能瓶颈。

### 解析

重点是说明统一治理价值及代价。只说“方便换模型”不完整，还应提到能力抽象泄漏和网关单点风险。

## 14. 热点内容生成怎么控制时效？

#缓存 #系统设计

### 知识点
- 事件触发、时效分级、版本、水位线、降级

### 答案

我会先定义业务可接受的新鲜度，比如秒级、分钟级或小时级，再决定用事件触发、定时刷新还是请求时生成。生成任务要携带源数据版本或时间水位，写入时做版本比较，防止旧结果覆盖新结果。热点可以预生成并短 TTL 缓存，源数据变更时主动失效；生成超时则返回带时间戳的上一版本或结构化数据，并明确标注新鲜度。最终用端到端延迟和过期内容比例监控，而不是只看任务是否执行。

### 解析

考察时效、一致性和成本之间的取舍。常见问题是只设置缓存 TTL，却没有防止异步任务乱序覆盖。

## 15. 如何防止敏感财务会议纪要越权泄露？

#安全 #权限

### 知识点
- 数据分级、最小权限、加密、输出控制、审计

### 答案

我会把会议音视频、转写和纪要都按敏感数据处理。采集时确认参会者和用途，存储与传输全程加密，检索前按用户、租户和文档 ACL 过滤；模型和处理服务只获得完成任务所需的最小数据。优先使用满足合规要求的部署和数据保留策略，必要时先脱敏再生成。生成结果仍要做权限继承、敏感信息检测和下载控制，并记录访问、分享和删除审计，防止纪要生成后变成新的泄露源。

### 解析

重点是端到端数据生命周期，而不只是 Prompt 脱敏。权限应在取数之前执行，输出也不能默认扩大原始材料的可见范围。

## 16. 截图里有多个金额时，如何避免取错？

#多模态 #Agent

### 知识点
- OCR、版面关系、字段约束、置信度、人工确认

### 答案

不能只让模型找“最大的数字”或第一个货币符号。我会先做 OCR 和版面分析，保留金额与标签、表格行列、币种和时间的空间关系，再根据业务字段定义提取，例如“含税总额”或“应付金额”。结果要通过格式、币种、合计关系和业务规则校验，并返回原图坐标作为证据。存在多个候选或置信度不足时，必须让用户确认，不能自动用于付款等高风险操作。

### 解析

考察多模态抽取的可验证性。正确做法是结合语义、布局和业务约束，而不是相信单次模型输出。

## 17. 租户删除数据后，Agent 摘要仍出现该内容，应该怎么处理？

#安全 #数据治理 #Agent

### 知识点
- 派生数据删除、缓存失效、索引清理、审计

### 答案

我会先停止受影响租户的相关检索和记忆写入，确认泄露范围并保全审计证据。然后沿数据血缘删除或失效原文、向量索引、缓存、会话记忆、摘要和评测样本等派生数据，并检查异步队列是否会把它重新写回。修复后用删除标识和回归用例验证所有读取路径都查不到。备份或法定留存数据按合规策略隔离，到期清除，但不能再进入在线检索和生成链路。

### 解析

重点是删除必须覆盖派生数据和异步回流。只删主表或重启缓存，无法保证后续生成不再出现该内容。

## 18. Agent 工具参数错误造成线上事故时，如何止损？

#安全 #Agent #故障处理

### 知识点
- 熔断、撤销、影响面、补偿、审批

### 答案

第一步是停止扩大影响：暂停相关工具、策略或租户流量，撤销未执行任务，并切换到只读或人工审批模式。随后通过 `trace_id`、`call_id` 和幂等键确认已执行范围，能回滚的立即回滚，不能回滚的执行经过验证的补偿流程，同时通知业务和安全负责人。事后要把参数做强类型校验、范围限制和风险分级，高风险写操作采用预览、二次确认、最小权限和小流量灰度。

### 解析

考察事故响应顺序：先隔离和止损，再评估、恢复和复盘。不能让同一个 Agent 在缺少约束时自行尝试反向操作。

## 19. 如何给不同业务做模型灰度？

#大模型 #灰度发布

### 知识点
- 场景分层、稳定分桶、指标、回滚

### 答案

我会先按业务场景建立基线，因为客服、搜索和代码生成关注的指标不同。流量按租户、用户或会话做稳定分桶，先内部影子流量，再从低风险、小比例逐步扩大；同一会话尽量固定模型，避免体验漂移。除质量评分外，还要看任务成功率、人工接管率、延迟、错误率、Token 成本和安全事件。每次灰度绑定模型、Prompt 和工具版本，达到止损阈值自动回滚，并保留对照组判断提升是否真实。

### 解析

重点是可归因的实验设计。随机切流但不固定会话、同时修改多个变量，会导致结果无法解释。

## 20. 如何排查 AI 导购展示价格与实际下单价格不一致？

#故障排查 #Agent

### 知识点
- 权威价格源、时效、缓存、促销规则、证据链

### 答案

先止损：暂停模型自由生成价格，让展示和下单都回到权威价格服务，并向受影响用户明确说明。排查时用商品、用户、渠道、时间和活动标识串起检索结果、工具调用、缓存版本、促销计算和订单快照，判断是模型编造、缓存过期、规则口径不同还是价格在会话中发生变化。长期设计上，模型只引用价格服务返回的结构化金额、币种、适用条件和有效时间，展示时带报价 ID，下单时服务端重新校验。

### 解析

价格是强一致的业务事实，不应由模型推断。关键是建立从展示报价到订单校验的可追溯标识。

## 21. 实时语音 Agent 如何降低首字延迟？

#语音 #性能优化

### 知识点
- 流式处理、端点检测、并行、连接复用、可撤销推测

### 答案

我会先分段测量采集、上行、ASR、模型首 Token、TTS 首帧和播放缓冲，找到真正瓶颈。优化上使用流式 ASR、较准确的端点检测、连接预热与复用，让编排在稳定的部分识别结果上提前准备上下文；检索和无副作用工具可以并行。模型先生成短而确定的开场，TTS 边生成边播放。任何基于中间识别的推测都必须可取消，不能为了快而提前执行有副作用的动作。

### 解析

这道题合并了两道首字延迟题。重点是端到端分解和流式并行，不能只笼统地说换更快模型。

## 22. 实时语音 Agent 应该怎么压测？

#语音 #性能测试

### 知识点
- 并发会话、网络劣化、延迟分位数、打断成功率

### 答案

压测单位应该是完整会话，而不是单个 HTTP 请求。我会构造不同音频长度、语言、静音比例、工具调用和打断行为，逐步提升并发会话数，并注入丢包、抖动、重连和下游超时。指标至少包括 ASR 首个稳定结果、模型首 Token、TTS 首帧、端到端首字的 P50/P95/P99，以及实时系数、断流率、打断成功率、错误率和单会话成本。还要长时间稳态测试，观察连接、队列、内存和限流是否恶化。

### 解析

考察真实负载模型和端到端指标。只压模型 QPS 无法发现音频长连接、播放和打断相关问题。

## 23. 视频理解如何控制成本？

#多模态 #成本优化

### 知识点
- 镜头切分、分层采样、缓存、任务路由

### 答案

我会先根据任务决定需要看什么，而不是把整段视频按固定高帧率送给大模型。先用镜头切分、OCR、语音转写和轻量模型筛出关键时间段，再对候选片段自适应采样；只有需要细节判断时才提高分辨率或调用更强模型。中间特征、字幕和片段摘要按视频版本缓存，重复问题直接复用。最后按任务成功率、漏检率、延迟和每分钟视频成本一起评估，避免单纯降采样导致质量不可接受。

### 解析

重点是任务驱动的分层处理。固定抽帧简单，但可能错过短暂事件，也可能对静态画面造成浪费。

## 24. 网络抖动场景下，Agent 应该怎么处理动作？

#可靠性 #Agent

### 知识点
- 幂等、状态查询、退避、降级、用户反馈

### 答案

Agent 不能因为响应没回来就假设动作失败。对读请求可以在预算内退避重试；对写请求先使用幂等键，并在超时后查询执行状态，再决定是否重试。连续抖动时要熔断或降级到只读、排队或人工确认，同时向用户显示“处理中”而不是虚假成功。关键动作应有服务端任务状态和最终回执，这样断线重连后可以继续查询，不依赖模型自己的记忆。

### 解析

考察不确定网络结果下的业务一致性。立即重复点击或重试写操作，可能造成重复执行。

## 25. 网络抖动造成音频乱序时怎么处理？

#语音 #计算机网络

### 知识点
- 序列号、时间戳、抖动缓冲、丢帧处理

### 答案

发送端要给音频帧附序列号和采样时间戳，接收端用有上限的抖动缓冲做短时间重排。超过等待窗口仍缺失的帧要标记丢失，根据编解码器做丢包隐藏、插入静音或丢弃，不能把迟到帧直接插回已播放位置。缓冲越大越稳定但延迟越高，所以应根据实时网络动态调整，并监控乱序率、丢包率、缓冲时长和端到端延迟。

### 解析

重点是用时序信息和抖动缓冲在完整性与实时性之间取舍，而不是无限等待或伪造缺失音频。

## 26. 为什么页面点击后不代表结果已经生效？

#前端 #Agent #可靠性

### 知识点
- 异步状态、业务回执、轮询或订阅、幂等

### 答案

点击只说明前端发起了操作，后面可能还有网络请求、队列、审批和异步任务。Agent 应以服务端的业务状态或可验证的页面条件为准：拿到任务 ID 后轮询、订阅事件，或调用查询接口确认最终状态。等待必须有超时和失败分支，写操作带幂等键；页面复杂时优先依赖稳定的 API、状态字段或可访问性属性，不要只等固定秒数或“网络空闲”。

### 解析

考察 UI 动作与业务完成的区别。网络空闲不一定表示异步任务完成，页面元素出现也不一定代表后端提交成功。

## 27. SSE 在前后端如何交互，事件格式怎么设计？

#SSE #前端 #后端

### 知识点
- `text/event-stream`、事件类型、序号、心跳、重连

### 答案

服务端以 `text/event-stream` 持续返回事件，每个事件可用 `event:` 声明类型、用 `id:` 标识序号、用 `data:` 携带 JSON，空行结束一条事件。原生 `EventSource` 适合 GET 单向订阅；如果要用 POST 提交复杂请求后流式读取，前端通常使用 `fetch` 读取响应流。业务事件可以统一包含 `event_id`、`task_id`、`type`、`timestamp`、`sequence` 和 `payload`；工具事件再放 `call_id`、工具名、状态、结果摘要或错误。还要设计心跳、完成、错误、重连和去重语义。

### 解析

这道题合并了 SSE 交互、推流格式和工具事件字段。字段是业务协议设计，不是 SSE 标准强制规定；前后端应共同维护版本兼容性。

## 28. 系统出现网络抖动而不是真故障时，Agent 怎么判断？

#可观测性 #计算机网络

### 知识点
- 多点探测、时间窗、错误分布、依赖健康度

### 答案

我不会根据单次超时直接判断服务故障，而会看一个短时间窗内的成功率、延迟分位数、丢包和重传，并比较不同实例、地域和探测点。如果失败是短暂、随机且重试后恢复，服务端资源和依赖又正常，更像网络抖动；如果错误持续集中在某个服务、实例或变更之后，则更像真实故障。自动处置需要连续窗口、最小样本量和多信号确认，证据不足时先降级观察而不是直接扩缩容或重启。

### 解析

考察如何避免单指标误判。关键是时间窗口、对照组和多源信号，而不是给某个延迟阈值下绝对结论。

## 29. 线上指标和离线评测结果不一致，怎么排查？

#评测 #可观测性

### 知识点
- 数据分布、版本、指标口径、链路差异、用户反馈

### 答案

我会先确认比较的是不是同一件事：模型、Prompt、工具、知识库版本和评测口径是否一致。然后比较线上请求与离线评测集的语言、长度、用户群、时间分布和难例比例，检查线上是否多了超时、权限、检索、缓存等链路问题。把线上失败样本按隐私规则脱敏后回流，人工复核并分桶，区分模型质量、系统可用性和业务目标。最后用固定基准集防回退，用滚动样本追踪真实分布变化。

### 解析

重点是区分数据分布偏移、版本不一致和指标口径不同。离线高分不等于线上任务成功率一定高。

## 30. 复杂页面加载时，Agent 应该怎么等待？

#前端 #自动化测试 #Agent

### 知识点
- 业务就绪条件、超时、重试、稳定选择器

### 答案

我会把“页面已加载”定义成可验证的业务条件，比如目标组件可见且可交互、关键 API 返回成功、加载状态消失或数据版本更新。等待采用条件轮询或事件通知，并设置总超时和明确错误；必要时只对幂等读取做有限重试。选择器优先使用稳定的可访问性角色或测试标识，避免依赖易变的 DOM 层级。对于持续有长连接的页面，不能把 network idle 当作唯一完成信号。

### 解析

考察浏览器自动化的稳定性。固定等待既慢又脆弱，单看网络空闲也容易被轮询、SSE 或懒加载误导。

## 31. 如何让用户实时看到工作流执行进度？

#SSE #工作流 #Agent

### 知识点
- 状态机、事件流、持久化、断线恢复

### 答案

我会先把工作流定义成明确状态机，例如排队、运行、等待输入、成功、失败和取消。每个节点开始或结束时写入持久化事件，再通过 SSE 或 WebSocket 把事件推给前端；事件包含任务 ID、节点 ID、序号、时间和可公开的进度摘要。断线重连后，前端先查询当前快照，再从最后序号补事件。进度必须来自后端真实状态，不能由前端计时器估算，敏感工具参数也不能直接展示。

### 解析

重点是“可靠状态 + 实时通知”两层设计。只依赖内存连接，断线后会丢失进度并造成前后端状态不一致。

## 32. Agent 系统怎么做权限过滤？

#安全 #Agent

### 知识点
- 检索前过滤、工具授权、最小权限、输出复核

### 答案

权限过滤要分层做。入口验证用户身份和租户；检索前根据文档或资源 ACL 过滤候选数据；工具调用前校验用户是否有该动作和目标资源的权限；输出前再检查是否包含不应暴露的信息。策略应集中管理、默认拒绝，并把用户、资源、动作和环境条件纳入判断。模型只能提出调用意图，不能自行授予权限或通过 Prompt 覆盖策略。

### 解析

考察授权是否贯穿读取、执行和输出。只在最后做文本过滤，既可能泄露上下文，也无法阻止越权工具操作。

## 33. 多租户应该选择物理隔离还是逻辑隔离？

- 风险分级、成本、性能、合规、混合隔离

### 答案

没有统一答案，我会根据数据敏感度、合规、客户规模、性能干扰和成本来选。普通租户可以共享集群，通过行级权限、独立命名空间、加密和配额做逻辑隔离；高敏感或大客户可以使用独立数据库、索引、密钥甚至独立部署。实践中常用分级混合方案，但无论哪种都要自动化测试隔离边界、监控资源干扰，并设计租户迁移能力。

重点是风险与成本权衡。物理隔离不等于天然安全，逻辑隔离也不等于一定不合规，关键在威胁模型和控制措施。

## 34. Agent 记忆怎么按租户隔离？

#Agent #多租户 #记忆

### 知识点
- 命名空间、访问控制、生命周期、删除传播

### 答案

每条记忆都要绑定租户、用户或主体、会话、来源和权限，存储与检索时强制使用这些维度，而不是让模型自行拼接过滤条件。向量索引、缓存键和异步任务采用相同命名空间；共享记忆必须经过显式授权。记忆还要有有效期、纠错和删除机制，源数据权限变化时同步失效派生摘要与向量。离线评测和调试环境也必须保持相同隔离。

### 解析

考察记忆的归属、访问和生命周期。只按会话 ID 隔离，无法防止跨用户、跨租户或离线数据串用。

## 35. Agent 想扩容但根因是下游限流，如何避免放大故障？

#运维 #可靠性 #Agent

### 知识点
- 因果判断、限流、背压、熔断、自动化护栏

### 答案

扩容前要先判断瓶颈在哪里。如果本服务 CPU、队列和处理能力正常，而下游持续返回限流或超时，扩容只会制造更多请求。我会先启用入口限流、队列背压、并发上限和熔断，重试使用预算与退避，必要时降级非核心功能。自动扩缩容策略应同时参考本服务资源、队列积压和下游健康度，并设置最大变更幅度、冷却时间和人工接管开关。

### 解析

考察自动化处置是否理解故障传播。仅根据队列长度扩容，可能形成重试风暴并压垮下游。

## 36. Agent 怎么判断告警是否需要立即处理？

#运维 #Agent

### 知识点
- 严重度、影响面、持续时间、SLO、处置风险

### 答案

我会综合看用户影响、核心业务范围、SLO 消耗速度、持续时间、扩散趋势和是否存在数据安全风险。单条告警先去重、聚合并结合变更和依赖状态，避免被瞬时噪声触发。满足预先定义的高危规则时可以自动执行低风险、可回滚动作；证据不足或动作不可逆时，只做信息收集、降级建议和通知升级。所有判断都应有规则版本、证据和处置审计。

重点是告警优先级不能只看阈值，还要看业务影响和错误预算。自动处理范围取决于动作风险，而非模型信心。

## 37. AI Agent 平台最重要的监控指标有哪些？

## 38. HTTPS 的工作原理是什么？

#HTTPS #TLS #计算机网络

### 知识点
- 身份认证、密钥协商、对称加密、完整性

### 答案

HTTPS 可以理解为 HTTP 运行在 TLS 保护的连接上。客户端连接服务端后，TLS 握手协商协议参数，服务端发送证书，客户端验证证书链、域名和有效期，并通过密钥交换推导出会话密钥；之后应用数据使用对称加密和完整性保护传输。这样主要解决窃听、篡改和服务端身份冒充问题。需要注意，证书验证不能被关闭，HTTPS 也不会自动修复应用层的鉴权、XSS 或服务端漏洞；HTTP/3 的 TLS 1.3 握手集成在 QUIC 中。

### 解析

重点是 TLS 同时提供机密性、完整性和身份认证。不要把 HTTPS 简化为“用证书直接加密所有业务数据”。

## 39. MCP 是什么，它在 Agent 系统中解决什么问题？

#MCP #Agent

### 知识点
- Model Context Protocol、能力发现、工具调用、资源与提示

### 答案

MCP 全称是 Model Context Protocol，是让 AI 应用以统一方式连接外部能力的开放协议。MCP 服务可以暴露工具、资源和提示，客户端进行能力发现并按协议调用，从而减少每接一个数据源或工具都写一套私有适配。它解决的是连接和交互标准化，不替业务完成认证、授权、参数校验和安全审计；生产系统仍要在网关与工具端落实这些控制，并处理超时、重试和版本兼容。

### 解析

这道题合并了两道 MCP 定义题。常见错误是把它写成 Modal Context Protocol，或把 MCP 当成具备自主决策能力的 Agent 框架。

## 40. RAG 评测闭环怎么自动运行？

#RAG #评测 #工程化

### 知识点
- 固定集、滚动集、分阶段指标、变更触发、发布门禁

### 答案

我会把评测做成流水线：保留一套版本化的固定基准集防止回退，再从线上失败、用户反馈和新业务中脱敏抽样形成滚动集。知识库、切分、Embedding、检索参数、重排、Prompt 或模型发生变化时自动触发，分别评估检索召回与排序、答案正确性、忠实度、引用质量、延迟和成本。低风险指标可自动判定，高风险与主观样本由人工复核；超过阈值才允许灰度发布，线上反馈再回流为新样本。

### 解析

考察从数据、指标到发布门禁的完整闭环。只用模型裁判且不做人工校准，容易产生系统性偏差和指标漂移。
