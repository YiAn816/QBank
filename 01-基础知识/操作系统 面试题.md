## 1. 什么是死锁？如何处理？

#操作系统 #并发编程

### 知识点
- 分类：操作系统、并发编程
- 四个必要条件
- 预防、避免、检测与恢复
- 工程排查方法

### 答案

死锁是多个执行单元各自持有一部分资源，又等待对方释放其他资源，最终形成循环等待，所有相关任务都无法继续。它通常需要同时满足四个条件：互斥、持有并等待、不可剥夺和循环等待。

处理思路有四类：破坏必要条件来预防死锁；在分配资源前判断是否安全，例如银行家算法；运行时检测等待图中的环；检测到后通过终止任务、回滚或抢占资源恢复。工程上更常见的做法是固定加锁顺序、缩小锁粒度、设置超时，并结合线程栈和锁等待图定位问题。

### 解析

面试回答应包含定义、四个必要条件和处理策略。还要区分死锁、活锁和饥饿：死锁是彼此等待，活锁是持续活动但没有进展，饥饿则是某个任务长期拿不到资源。

## 2. 端侧 Agent 的资源控制要关注哪些指标？

#系统设计 #端侧AI #性能优化

### 知识点
- 分类：系统设计、端侧 AI、性能优化
- 延迟、内存、CPU/GPU/NPU 和功耗
- 包体、存储、网络和后台资源
- 设备分层与动态降级

### 答案

我会从体验和资源两方面看。体验侧关注启动时间、首个有效响应、端到端延迟和卡顿率；资源侧看内存峰值、CPU/GPU/NPU 占用、功耗、温升、包体与磁盘，以及网络流量和后台唤醒次数。

这些指标要按设备档位、系统版本和前后台状态分层统计，尤其关注 P95、P99 和长时间运行后的变化。超过预算时可以减少上下文、切换更小模型、降低并发或转到云端，并保证降级后的功能和隐私边界清晰。

### 解析

端侧系统首先受设备预算约束。只报告平均 CPU 或模型准确率不够，还要考虑尾延迟、内存峰值、热降频、耗电和不同设备之间的差异。

## 3. 多个 Agent 同时修改状态时，如何避免冲突？

#分布式系统 #并发控制 #AI-Agent

### 知识点
- 分类：分布式系统、并发控制、AI Agent
- 单一事实来源和状态机
- 乐观锁、CAS 或事务
- 字段所有权与事件顺序
- 冲突检测和补偿

### 答案

我会先定义一个权威状态存储和显式状态机，Agent 只能提交状态变更请求，不能各自在对话里维护一份“真相”。更新时携带版本号，通过 CAS、乐观锁或事务保证并发写入不会静默覆盖。

还要划分字段所有权：每个 Agent 只写自己的工作区，共享字段由编排器或专门服务合并。发生版本冲突时重新读取最新状态并重算，不能盲目重试；涉及外部副作用时还需要幂等键、事件日志和补偿机制。

### 解析

考点是并发控制和状态所有权。锁只是手段之一，分布式系统里还要考虑版本、事件顺序、重试以及已经产生的外部副作用。

## 4. 多轮语音对话中，如何处理用户长时间静默？

#语音交互 #状态机

### 知识点
- 分类：语音交互、状态机
- 区分短暂停顿、离开和网络异常
- 分级超时与提示
- 保存任务状态并释放资源
- 恢复时重新校验上下文

### 答案

我会把静默作为状态机事件，而不是立刻判定会话结束。短暂停顿可能是用户在思考，可以继续等待；达到第一档超时后给一次简短提示；继续无响应则暂停或结束语音会话，并释放 ASR、TTS 和模型资源。

同时要结合网络状态、VAD 结果和客户端前后台状态，区分用户没说话、麦克风不可用和连接中断。长任务应保存目标、已完成步骤和待确认事项，用户回来后重新确认关键状态再继续。

### 解析

这道题的核心是分级超时、原因判断和资源释放。“静默”不等于“离开”，恢复任务时也不能直接沿用可能已经过期的页面或业务状态。

## 5. 多 Agent 系统如何避免上下文互相污染？

#AI-Agent #系统设计

### 知识点
- 分类：AI Agent、系统设计
- 最小必要上下文
- 私有工作区与结构化共享状态
- 来源、版本和置信度
- 不可信内容隔离

### 答案

每个 Agent 只接收完成自己任务所需的信息：规划 Agent 看目标和约束，执行 Agent 看子任务和工具结果，审核 Agent 看产物、证据和验收标准。共享层保存任务 ID、状态、证据引用和决策结果等结构化数据，不广播所有 Agent 的完整推理文本。

共享内容还要带来源、版本和置信度，不可信网页或文档要标记为数据，不能覆盖系统指令。Agent 的临时草稿放在私有工作区，只有经过校验的结果才能进入公共状态。

### 解析

考点是最小权限原则在上下文中的应用。隔离既降低噪声和 Token 成本，也能阻止一个 Agent 的错误或恶意输入扩散到整个系统。

## 6. 进程、线程和协程有什么区别？

#操作系统 #并发编程

### 知识点
- 分类：操作系统、并发编程
- 地址空间和资源隔离
- 操作系统调度与用户态调度
- 切换成本和故障边界
- 并发不等于并行

### 答案

进程拥有独立的虚拟地址空间和系统资源，隔离最强，但创建、通信和切换成本相对高。线程属于进程，共享地址空间，由操作系统调度，通信方便，但一个线程的内存错误可能影响整个进程，并且共享数据需要同步。

协程是更轻量的用户态执行单元，通常由语言运行时或事件循环调度，切换成本低，适合大量 I/O 等待任务。协程提供的是高并发组织方式，不会自动让 CPU 密集代码并行；要利用多核，还要看运行时、线程或多进程模型。Go 的 goroutine 属于运行时调度的轻量任务，但实现细节不应简单等同于所有语言中的协程。

### 解析

回答应从隔离、调度、通信、切换成本和并行能力比较。需要避免“进程是资源分配最小单位、线程是调度最小单位”这种过度绝对的口号式表述。

## 7. 任务优先级应该怎么设计？

#操作系统 #调度系统

### 知识点
- 分类：操作系统、调度系统
- 紧急度、截止时间、业务价值和资源成本
- Aging 与公平性
- 优先级反转
- 抢占与不可中断区间

### 答案

优先级不能只由一个固定数字决定。我会综合业务紧急度、截止时间、用户等级、任务等待时长和资源成本计算，并按任务类型设置独立队列和并发配额。低优先级任务随着等待时间增加可以逐步提升优先级，避免饥饿。

如果高优先级任务依赖低优先级任务持有的锁，要考虑优先级继承等机制处理优先级反转。是否允许抢占还取决于任务能否安全暂停和恢复，不可逆操作不能随意中断。

### 解析

面试官关注时效、公平和资源效率之间的平衡。完整回答应提到饥饿、优先级反转、抢占边界以及监控和动态调整。

## 8. 用户频繁打断语音 Agent，但系统仍继续播放，怎么排查？

#语音交互 #故障排查

### 知识点
- 分类：语音交互、故障排查
- VAD、回声消除和打断判定
- 取消信号全链路传播
- TTS 缓冲与工具状态
- Trace 和延迟分段

### 答案

我会沿打断事件的链路逐段排查。先看 VAD 是否检测到用户说话，以及回声消除是否把播放声音误判成用户语音；再看打断事件是否到达会话状态机，是否真正取消 LLM 生成、TTS 合成和播放器缓冲。

如果还有工具任务，要确认取消信号是否传播到尚未执行的计划，已经提交的不可逆动作则按业务状态处理。通过同一会话的时间线对齐 VAD、ASR、LLM、TTS 和播放日志，就能判断延迟或丢事件发生在哪一段。

### 解析

“停止播放”涉及检测、事件传递、生成取消、音频缓冲和业务状态多个环节。只调 VAD 阈值可能造成误打断，必须用分段 Trace 定位。

## 9. 如何限制第三方 MCP Server 访问本地文件和网络？

#安全 #沙箱 #MCP

### 知识点
- 分类：安全、沙箱、MCP
- 独立进程或容器隔离
- 文件、网络和系统调用最小权限
- 临时凭证与密钥代理
- 审计、配额和版本治理

### 答案

我会把每个第三方 MCP Server 运行在独立的受限进程、容器或沙箱中，默认禁止访问宿主文件和公网。根据实际工具能力只挂载必要的只读目录，网络通过代理限制到允许的域名和端口，并限制系统调用、子进程、CPU、内存和执行时间。

敏感凭证不写入镜像或长期环境变量，而由凭证代理按请求发放短期、最小权限令牌。所有工具调用、文件访问和出站请求都要审计；升级 Server 前还要校验来源、固定版本并重新做权限评审。

### 解析

沙箱与白名单只是基础，完整的纵深防御还包括临时凭证、资源配额、供应链治理和审计。域名白名单也要防 DNS 重绑定和重定向绕过。

## 10. 实时导航中，语音 Agent 如何协调地图事件和用户语音？

#语音交互 #事件驱动架构

### 知识点
- 分类：语音交互、事件驱动架构
- 统一事件模型和动态优先级
- 安全事件可抢占
- 播报冲突和取消传播
- 过期事件丢弃与状态复核

### 答案

我会把地图事件、用户语音、TTS 播放和工具状态统一成带时间戳、优先级、有效期和取消标记的事件流。临近转弯、危险提醒等安全事件可以抢占普通问答；用户开始说话时，非紧急播报应暂停，避免双方同时发声。

抢占后还要处理旧事件是否仍有效。例如已经错过的转弯提示不能恢复播放，未完成的用户问题则可以在安全提示结束后继续或重新确认。调度策略要能解释，并通过驾驶场景仿真测试抢占、连续事件和网络延迟。

### 解析

核心不只是“放进一个优先级队列”，还包括事件有效期、抢占、恢复和取消。安全优先也不能无限打断，系统需要合并和抑制重复提示。

## 11. 为什么多 Agent 系统更难排错？

#AI-Agent #可观测性

### 知识点
- 分类：AI Agent、可观测性
- 非确定性和跨组件传播
- 完整 Trace 与因果关系
- Prompt、模型、工具和状态版本
- 可重放与分层评测

### 答案

因为一次结果通常经过规划、多个 Agent、工具和共享状态，错误会跨节点传播，最后报错的 Agent 不一定是根因；模型本身还有非确定性，同样输入也可能走不同路径。

我会为每次任务生成 Trace ID，记录每个步骤的输入摘要、Prompt 和模型版本、工具参数与结果、状态读写、延迟和错误，并保留父子调用关系。排查时先确定第一个偏离预期的节点，再用固定模型参数、工具桩或状态快照做可控回放，而不是只看最终对话。

### 解析

考点是分布式追踪和 AI 非确定性的结合。日志数量多不等于可观测，关键是版本、因果关系、状态变化和可重放性。

## 12. Python 为什么会受到 GIL 限制？

#Python #并发编程

### 知识点
- 分类：Python、并发编程
- 默认启用 GIL 的 CPython 构建
- I/O 并发与 CPU 并行的区别
- 原生扩展可释放 GIL
- CPython 3.13 起提供 free-threaded 构建

### 答案

严格来说，GIL 是 CPython 的实现机制，不是 Python 语言的统一规定。在默认启用 GIL 的 CPython 中，同一解释器进程通常只有一个线程执行 Python 字节码，所以纯 Python 的 CPU 密集任务很难通过多线程充分利用多核；I/O 密集任务在等待时会释放 GIL，因此仍能从线程并发中受益，一些原生扩展也会主动释放它。

CPU 密集任务可以根据场景使用多进程、会释放 GIL 的原生库，或评估 free-threaded CPython。自 CPython 3.13 起已经提供可禁用 GIL 的 free-threaded 构建，但仍要考虑扩展兼容性、线程安全和性能开销，不能直接认为所有 Python 多线程都不再受限制。

### 解析

回答要限定在 CPython 和具体构建上，并区分并发与并行。GIL 简化了部分解释器对象管理，但不是应用层线程安全保证；共享数据仍应使用明确的同步机制。

## 13. 文件上传到 Agent 后，如何保证安全？

#安全 #文件处理 #AI-Agent

### 知识点
- 分类：安全、文件处理、AI Agent
- 大小、真实类型和压缩包限制
- 恶意软件、解析器和 Prompt Injection 防护
- 沙箱解析与内容隔离
- 租户权限、血缘和生命周期

### 答案

入口先限制大小、数量和扩展名，并检查真实文件类型，防止伪装后缀、压缩炸弹和路径穿越；随后做恶意软件扫描，解析过程放在无网络、低权限、有限资源的沙箱里，不能让不可信文件直接接触主服务。

解析出的文本、图片、切片和向量都要继承租户、权限、来源和保留期限。文档中的指令属于不可信数据，要防止间接 Prompt Injection；敏感信息按策略检测、脱敏或阻止入库。删除原文件时，也要同步清理派生数据、索引和缓存。

### 解析

文件安全是从上传、解析、存储、检索到删除的全生命周期问题。只做病毒扫描无法覆盖解析器漏洞、权限泄露和文档提示词注入。

## 14. 多租户系统如何做资源限流和配额隔离？

#多租户 #限流 #资源隔离

### 知识点
- 分类：多租户、限流、资源隔离
- 租户、用户、接口和资源池多级限制
- 速率、并发、Token 和工具配额
- 公平队列与系统预留容量
- 可解释降级、告警和容量规划

### 答案

我会把限制拆成多个维度：租户和用户级 QPS、并发任务数、Token 或模型用量、工具调用次数，以及共享线程池、GPU 和队列的资源额度。调度层采用加权公平队列，并保留系统容量，避免一个大租户把所有资源占满。

超额请求按业务优先级排队、限流或降级，同时返回明确原因和重试建议。监控要区分租户滥用、突发流量和系统整体容量不足；不同套餐可以有不同配额，但都不能突破平台安全上限。

### 解析

资源隔离也是租户隔离的一部分：数据没有串租户，不代表某个租户不能造成拒绝服务。完整回答应覆盖多维配额、公平调度、预留容量、降级和可观测性。

## 15. 如何避免多个 Agent 对同一资源重复操作？

#AI-Agent #幂等 #并发控制

### 知识点
- 分类：AI Agent、幂等、并发控制
- 稳定业务幂等键
- 原子去重、唯一约束或状态机
- 锁与租约
- 状态未知时先查询

### 答案

首先为同一个业务意图生成稳定的幂等键，让不同 Agent 或重试请求都携带同一个键。最终写入服务通过唯一约束、幂等记录或状态机原子判断是否已经执行，重复请求直接返回原结果。

对需要长时间独占的资源可以加带超时和续约的分布式租约，但锁不能代替业务幂等，因为持锁方崩溃或网络超时后仍可能重复。结果未知时先查询资源状态，再决定继续、补偿还是人工处理。

### 解析

只说“加锁”不完整。锁解决并发互斥，幂等解决重复请求，状态机和唯一约束则提供最终写入保障，三者的职责不同。

## 16. 执行失败后，如何做回放排查？

#可观测性 #故障排查

### 知识点
- 分类：可观测性、故障排查
- 输入、版本、状态和动作轨迹
- 页面、网络和工具证据
- 脱敏与访问控制
- 确定性回放和外部副作用隔离

### 答案

为了回放，我会记录任务输入及来源、Prompt 和模型版本、推理参数、状态快照、每一步动作、工具参数与结果、网络日志以及必要的页面截图或 DOM。所有记录通过同一个 Trace ID 和时间线关联，并对敏感数据脱敏和限制访问。

回放时要固定模型和依赖版本，并用工具桩或沙箱隔离外部副作用，避免排查过程再次下单或修改数据。目标是找到第一个偏离预期的步骤，而不是只重复最后一个报错动作。

### 解析

回放能力依赖事前的版本和证据记录。对于非确定性模型，完全逐字复现未必可行，但应能够复现输入、状态、工具行为和关键决策条件。

## 17. Agent 生成修复命令后，为什么不能直接执行？

#安全 #运维 #AI-Agent

### 知识点
- 分类：安全、运维、AI Agent
- 模型输出不可信
- 语法、权限、影响范围和环境校验
- 只读预检、模拟执行与审批
- 最小权限、幂等、回滚和审计

### 答案

模型生成的命令可能语法正确但目标错误，也可能基于过期上下文、扩大影响范围或被提示词注入操控，所以必须把它当成不可信建议。执行前要解析命令和参数，确认目标资源、权限、环境、影响范围和前置条件，并先做只读检查或 Dry Run。

生产环境默认需要审批，高风险命令使用双人确认或变更系统；只有经过验证的低风险白名单动作才允许自动化，并且使用最小权限凭证、幂等保护、超时、回滚方案和完整审计。

### 解析

考点是纵深防御和爆炸半径控制。Prompt 中写“请谨慎执行”不是安全机制，真正的边界必须由执行平台、权限和审批流程强制保证。
